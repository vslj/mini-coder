# 不用 SDK，手写一个 mini Claude Code（二）：给模型一台计算机，再修一堵墙

> 这是 mini-coder 系列的第二篇。上篇（地基篇）我们从裸 HTTP 请求开始，写出了一个会聊天、会流式输出、会重试的 REPL——但它只会动嘴。这一篇让它动手：读、写、修改你磁盘上的文件。而"AI 能改你的文件"这件事，立刻带来一个比"怎么做到"更重要的问题：**凭什么放心让它改？**
>
> 所以这篇的两半是配套的：前一半，**给模型一台计算机**（四个文件工具）；后一半，**在计算机外面修一堵墙**（路径防护、权限确认、敏感文件闸）。墙修完你会发现，最精彩的部分不是墙本身，而是模型面对墙时的种种反应——那才是理解 Agent 的钥匙。
>
> 和上篇一样：面向没正经调过 LLM API 的你，先跑起来再拆解；文中每个数字、每段对话都是我自己跑出来的原始记录（key 一律脱敏成 sk-xxx），可复现、可对照。

## 0. 先跑起来（十分钟）

准备两样东西，跟上篇一样：

1. **Node.js**（20 以上版本），终端里 `node -v` 能看到版本号就行；
2. **一个 LLM API key**——门禁卡，别发群里、别截图、别提交进 git。

然后三步：

```bash
# 1. 拿到代码
git clone https://github.com/vslj/mini-coder.git && cd mini-coder
# 本文对应的版本（可省略，最新代码同样能跑通本文全部实验）
git checkout v0.3.2

# 2. 安装依赖（依然零运行时依赖，几秒装完）
pnpm install

# 3. 配置钥匙
cp .env.example .env
# 打开 .env，把 sk-xxx 换成你的真实 key
```

启动：

```bash
pnpm dev
```

这次的启动横幅多了一行，值得停下来看一眼：

```
mini-coder v0.3.0
  模型      mimo-v2.5-pro
  OpenAI    https://api.xiaomimimo.com/v1

  密钥      sk-xxx（已脱敏展示）
  工作区    D:\workspace\code\mini-coder（文件工具的操作边界）
```

**"工作区"就是你的启动目录**：这程序的文件工具，只允许操作这个目录里的东西——出了这个目录就动手不了。它不是随便说说的，第三节我们会拿三种刁钻路径去撞这堵墙。第一次玩建议找个练手目录，测试产生的 hello.txt 之类的文件别提交进 git 就行。

先看一眼它现在有哪些本事：

```
> /tools
已注册工具（agent 模式：开）:
  get_time —— 获取当前时间
  calculate —— 四则运算
  read_file —— 读取工作区内某个文本文件的内容……
  list_files —— 列出工作区内某个目录的内容……
  write_file —— 把文本内容写入工作区内的某个文件…… 🔒
  edit_file —— 编辑工作区内的某个文本文件…… 🔒
（🔒 = 写类工具，执行前需要确认）
```

好，重头戏。对它说：

```
> 创建一个 hello.txt，写三行你对自己的介绍
```

你会看到一串新画面：一行暗淡的 `⚙ write_file(...)`（模型要写文件了）；然后一块**红绿相间的预览**；然后一个**确认弹窗**：

```
【新文件】hello.txt（3 行）
我是 mini-coder，一个运行在终端里的极简编码助手。
……
允许执行 write_file 吗？(y=允许 / n=拒绝 / a=本会话都允许)
```

敲 `y`，文件才真正落盘。然后注意看：模型紧接着又自己调了一次 `read_file`，把刚写的内容读回来核对了一遍，最后才向你汇报"已完成"。

刚才这一分钟里出现了三个画面：**红绿 diff、y/n/a 弹窗、模型自己回头检查**。本文剩下的所有内容，就是把这三件事讲透。

## 一、它是怎么"动手"的？

先补上上篇结尾埋的伏笔。上篇说过，模型回答结束时 `finish_reason` 会变成 `"stop"`；但如果模型想用工具，它会变成 `"tool_calls"`，同时附带一份"我想调用 write_file，参数是这些"的清单。

然后发生的事，是整个 Agent 世界的核心循环（`src/agent.ts` 的骨架）：

```ts
for (let round = 1; round <= maxRounds; round++) {
  const result = await provider.chat(messages, { system, tools, signal });

  // 模型不要工具：自然停，把最终回答入历史，回合结束
  if (!result.toolCalls?.length) {
    messages.push({ role: "assistant", content: result.content });
    return { content: result.content, stopped: "answer", ... };
  }

  // 模型要工具：先原样回填它的话，再逐个执行、逐条回传结果
  messages.push({ role: "assistant", content: result.content, toolCalls: result.toolCalls });
  for (const call of result.toolCalls) {
    const outcome = await tools.execute(call.name, call.args);
    messages.push({ role: "tool", toolCallId: call.id, content: outcome.content });
  }
  // 然后回到循环开头，把带着工具结果的历史再发给模型："看，结果在这，接着想"
}
```

想 → 做 → 看 → 再想。这个循环画出来就是：

```
        ┌──────────────────────────────────────────────┐
        │                                              │
        ▼                                              │
   模型看历史 ──▶ 还要工具吗？──否──▶ 输出最终回答，回合结束
        │是
        ▼
   程序执行工具 ──▶ 结果回填历史 ─────────────────────┘
                  （模型下一轮就能看到结果，决定下一步）
```

模型看到工具结果后可能还要下一个工具（比如先 `read_file` 再 `edit_file`），那就再来一圈，直到它不再要工具为止。我实测里甚至出现过一轮请求里模型**同时**要求"读 hello.txt + 写 hello.txt"两个工具，循环逐个执行、逐条对号回传——一次说话点多个菜是常态。

这里有一个本篇最重要的认知，请刻在脑子里：

**模型从头到尾没有碰过你的文件系统。它只是输出了一段 JSON，说"我想调用 write_file，参数是这样这样"。真正动手的，是你的程序。**

模型是点菜的，你的程序是后厨。这个分工在平时看不出来，但我有一次故意关掉了工具功能（`/tools off`）再让它读文件，它的输出让我愣了半天：

```
> /tools off
（agent 模式已关闭——纯聊天流式）
> 读一下pnpm-lock.yaml
[思考] 用户要求读取 pnpm-lock.yaml 文件。……
<tool_call>
<function=read_file>
<parameter=path>pnpm-lock.yaml</parameter>
</function>
</tool_call>
```

它在**演**。工具声明已经关了，但历史里全是上一阶段工具调用的往返记录，模型照着记忆把调用"演"成了正文里的一段文字——连格式都是它的训练数据里工具调用的原始模板语法（`<tool_call><function=...>`），平时根本轮不到用户看到的那种内层格式。当然，这段"调用"没有人执行，文件一个字节都没动。

这个意外一举验证了三件事：①能力要靠程序在请求里声明 schema 才激活，但**模仿历史是模型的默认习性**；②演出来的调用只是文字——**客户端是唯一执行者**；③工具调用的本质，确实是"特殊格式的文本 → 程序解析 → 程序执行 → 结果回填"。

好，现在问题掉了个头：既然执行权百分之百在我们程序手里，那"敢不敢让 AI 改文件"这个问题，答案不在模型那边——**在于我们的程序怎么执行**。这就是接下来的全部内容。

## 二、写之前，先给你看一眼：diff

你刚才在弹窗里看到的红绿预览，就是 diff。git 提交前你敲 `git diff` 看到的那种输出——绿色是新增的行，红色是删掉的行。Claude Code 每次要改你文件时弹的那个预览，也是同一个东西。

你可能会想：这玩意儿直接 `npm install diff` 不就完了？但我们这个项目的卖点是**零运行时依赖**，而且——剧透一下——这个算法的核心只有二十来行，被需求逼出来的原理正是本文想讲的。自己写。

**diff 的本质是"保留尽量多的公共行"。**两个文件，旧的和新的，找出一套"删几行、加几行"的方案，让没变的行尽量多。这个"尽量多"有专门的算法：**LCS，最长公共子序列**。直觉版本：拿旧行和新行一张一张比对，相同的就是两边都保留的行；不同的地方，删旧的、加新的。

```ts
// dp[i][j] = a[i..] 与 b[j..] 的最长公共子序列长度（倒着填表）
for (let i = n - 1; i >= 0; i--) {
  for (let j = m - 1; j >= 0; j--) {
    dp[i]![j] = a[i] === b[j] ? (dp[i + 1]![j + 1] ?? 0) + 1
                             : Math.max(dp[i + 1]![j]!, dp[i]![j + 1]!);
  }
}
// 回溯：相同 → 原样保留；不同 → 朝公共部分更长的一侧走（删旧行或加新行）
```

但直接这么写有个工程地雷：这张 dp 表是 n×m 的格子，两个 5000 行的文件就是 2500 万格。所以加了两道保险：

1. **先掐公共前后缀**。真实的编辑几乎总是只动文件中间一小段——头尾几十行原封不动。把它们直接标记为"不变"，不进算法。实测一个 3000 行的文件只改 1 行，前后缀掐完后，中间送进算法的规模退化到 1×1。
2. **降级兜底**。中间段仍超过 400 行就放弃精细计算，直接"整段删除 + 整段新增"。不追求最优展示，但绝不把内存吃爆。

这套东西对应的场景很具体：模型想覆盖重写一个文件时，弹窗里显示的不是"新文件长这样"，而是**旧文件和新文件的逐行对比**。我的实测记录：

```
> 重新覆盖文件内容，文件内容是你的自我介绍
⚙ write_file(hello2.txt, "我是 mini-coder，……")
(+1 / -3 行)
- 1 │ 欢迎来到王者荣耀
- 2 │ 你不要玩王者荣耀这种耗费时间的游戏了……
- 3 │ 人生有好多有意思的事情，不要沉迷游戏追
+ 1 │ 我是 mini-coder，一个运行在终端里的极简编码助手。……
允许执行 write_file 吗？(y=允许 / n=拒绝 / a=本会话都允许)
```

一屏看懂"它要把我文件里的什么换成什么"。diff 预览对"整文件替换"和"精确替换某一行"同样工作——它不是 edit 的专属，是所有写操作的标配。

顺带交代一个只在 Windows 上撞得到的坑，文档里不会有：很多 Windows 文件的换行是 `\r\n`（CRLF），而模型给的查找文本用的是 `\n`。如果不做处理，`edit_file` 会**永远找不到要替换的文本**——工具永远报"找不到"，模型一头雾水。修法是把读进来的内容统一归一成 LF 再比较。这类问题不撞一次真的想不到。

还有一个容易被忽略的设计点：edit 的"给你看的预览"和"实际执行"走的是**同一套替换逻辑**（同一个函数，先算出替换后的全文，预览画 diff，执行写文件）。听起来理所当然，但反过来想：如果预览和执行是两套代码，早晚有一天你看到的和它做的不是同一件事。预览系统最大的美德是诚实。

## 三、三道关卡

现在修墙。模型要动你工作区里的文件，中间隔着三道关卡——每一道都是我在用 Claude Code 时见过、这次亲手造出来的（上篇说过：确认发生在程序侧，模型无法绕过，现在你知道"程序侧"具体长什么样了）。先看全景：

```
 模型："我想写 hello.txt"
        │
        ▼
 ┌─ 第一关 路径逃逸防护 ── resolve 之后校验，../ 和绝对路径全部现形
 ├─ 第二关 权限门 y/n/a ── diff 预览给你看 + 你点头（a = 本会话免确认）
 ├─ 第三关 敏感文件闸 ─── 连读都拒（.env 进上下文 = key 出门）
 ▼
 真正写盘
```

### 关卡一：路径逃逸防护

文件工具拿到的路径是模型给的字符串。模型会给你什么？最普通的当然是 `hello.txt`，但它也会给你 `../.env`（"读一下上级目录的配置"）或者一个 `D:\任何地方\任何文件` 的绝对路径。不加防护的话，"工作区边界"就是一句空话。

防护写起来只有几行，但有个关键的位置讲究——**必须在路径解析（resolve）之后做检查，而不是之前**：

```ts
function resolveSafe(root: string, path: string): string {
  const target = resolve(root, path);   // 先把任何花里胡哨的写法解析成绝对路径
  const rootAbs = resolve(root);
  if (target !== rootAbs && !target.startsWith(rootAbs + sep)) {
    throw new Error(`路径越界：只能操作工作区内的文件（... 不在工作区内）`);
  }
  return target;
}
```

为什么不能在字符串层面检查？因为字符串是会骗人的：`src/../README.md` 看起来出了 src 又回来了，`./src/../README.md` 带个无关的 `./`，绝对路径干脆绕过相对逻辑——这些花招在**解析后**都会现出原形（全部变成同一个绝对路径），在解析前用字符串判断，永远堵不完。

我拿三种花招实测了一圈：

```
> 读一下./src/../README.md的内容
⚙ read_file("./src/../README.md") → 成功（解析后还在工作区内，放行）

> 读取src/../../说明.md
⚙ read_file("src/../../说明.md") ✗ {"error":"路径越界：只能操作工作区内的文件（..\说明.md 不在工作区内）"}

> 你能读到D:/workspace/code/mini-coder/package.json吗？
⚙ read_file("package.json") ← 模型自己把绝对路径换算成了相对路径
模型答："能"
```

第三条最有趣：工作区内文件的绝对路径本来是放行的，但模型没赌这个，**自己把绝对路径换算成了相对路径**——行为完全正确，但没走我设计的路。它"替考"了这道为它准备的题。这也是 Agent 的常态：你为一种用法修的墙，它经常从你想不到的方向绕过去，而且有时候绕得还挺优雅。

另外注意报错信息里的路径显示：错误里出现的全是从工作区根算起的相对路径，绝不打印本机绝对路径。上篇提过工具报错回传会泄漏本机环境信息，这里就是那笔债的偿还处。

### 关卡二：写类确认（y/n/a）

读文件、列目录不需要确认——**读工作区是 agent 的基本权利**（原因见第七节的"意外收获"）。但写和改必须过人这一关：

- `y` = 允许这一次；
- `n`（或随手回车）= 拒绝这一次；
- `a` = **本会话内该工具不再确认**。

`a` 的记忆存在程序内存的一个 Set 里。这里有个我实测出来的、初看有点违反直觉的现象：

```
> 创建hello3.txt并且写上hello china
弹窗 a → （本会话内 write_file 将不再确认）→ 执行成功
> /clear
(历史已清空)
> 创建hello4.txt并且写上hello shanxi
⚙ write_file(hello4.txt) → 直接执行，零确认
```

还记得上篇的吗？`/clear` 之后模型会"失忆"，暗号都装不认识。**但权限记忆跨 `/clear` 存活了**——清空历史之后，写文件依然不弹窗。

为什么？因为"会话状态"根本不是一层，是好几层：`/clear` 清的是 **messages 数组**（对话历史，会发给模型的那份）；权限记忆是**独立于历史的另一份程序状态**，压根不在发给模型的请求里。失忆的是模型，不是程序。上篇说"模型服务端无状态，记忆是客户端给的"，这篇再补一刀：**客户端手里的状态也不止一份，各有各的生命周期**。

还有个保守的设计决策：`a` 的授权**不落盘**，程序一重启就全部作废，回到逐次确认。危险能力默认收紧，想常开就得每次重新按——安全设计的默认姿态。

### 关卡三：敏感文件闸

前两道关卡守的都是"写"。这一道例外：**有些文件，连读都不许**。

```
function assertNotSensitive(root, absPath) {
  if (/^\.env/.test(文件名)) {
    throw new Error(`${文件名} 是敏感文件（可能含密钥），mini-coder 拒绝读写它`);
  }
}
```

为什么读都不行？回想上篇的结论：对话历史每一轮都**全量重发**给模型服务器。`.env` 里是你的 API key——一旦被 `read_file` 读进上下文，它就会随下一轮请求**原样发出去**，离开你的电脑。对一个密钥安全零容忍的项目，这条路必须彻底焊死。

实测效果：

```
> 读取.env的内容
⚙ read_file(".env") ✗ mini-coder 拒绝读写它
模型：解释这是密钥文件，主动建议去读 .env.example（专门给人看的示例配置）
```

注意模型的反应：它没有把拒绝当成任务的终点，而是顺着墙找到了指示牌——去看示例文件。这是我喜欢的一个说法：**安全设计不是一堵墙，是一堵带指示牌的墙**。拒绝消息里给出替代路径，模型就把出路接住了。

但这堵墙有个值得摊开讲的误伤：它连 `.env.example`（给人看的示例文件，里面根本没密钥）也拦了。因为我的规则是文件名以 `.env` 开头就拒绝——一行正则，前缀匹配，零绕过。要放行 `.env.example` 也行，但规则就从"前缀匹配"变成"枚举例外"，每加一个例外都是一道新裂缝。我的取舍是**宁可错杀一个示例文件，换"零漏网"**。安全规则的宽松度没有标准答案，但必须是一个显式的、想清楚的决策，而不是顺手写出来的副作用——实测里模型对 `.env.example` 被拦的回答很诚实："不能。虽然文件存在，但被安全策略拒绝读取"。

## 四、拒绝不是终点：把错误喂回去

三道关卡都会产生"失败"：路径越界抛错、用户按 n、敏感文件被拒。接下来发生的事，是 Agent 和普通程序最大的观念差异：

**工具执行失败不是异常，是一种结果。程序不崩溃、不重试、不弹错误对话框——把失败原因打包成一条消息，喂回给模型，让它自己想办法。**

```
 工具报错 ──▶ 打包成 {"error":...} 回填历史 ──▶ 模型看到错误
                    ▲                              │
                    │        换个方案再试           │
                    └──────────────────────────────┘
                        （还错？再喂回，循环到做对为止）
```

调研过的四个同类实现（Amp、smolagents、mini-swe-agent、Claude Agent SDK 剖析文）在这一条上无一例外。

这条机制的价值，看实测才知道。上面那个路径越界的报错喂回去之后，模型的反应是：

> 工作区根目录下就有一个 说明.md，需要我读这个吗？

它不光"知道了失败"，还从报错信息里的相对路径推断出了正确目标。错误喂回的价值不只是"通知"，是**给模型一条线索**。

用户按 `n` 拒绝的场景更讲究。程序喂回去的是一条精心措辞的消息（逐字）：

```json
{"error": "用户拒绝了这次操作。不要原样重试；如果仍有必要，请换一种方案或向用户说明。"}
```

注意这消息里写了三件事：发生了什么（用户拒绝）、不该做什么（别原样重试）、该做什么（换方案或问我）。措辞不是客气，是**行为设计的杠杆**。实测里同一套措辞喂出去，模型的反应高度一致——被拒后一句辩解都没有：

> 操作被拒绝了，文件没有被创建，需要时随时找我。

或者反过来把选择权交回给你：

> 您是希望将这段话添加到文件中吗？

而我按 `n` 之后说"继续"，它不重试刚才被拒的 edit，直接**换了方案**——改用 write_file 把整个文件重写一遍，把同样的内容加进去了。拒绝消息里"换一种方案"的引导，被一字不差地照做了。

这套机制也有吃瘪的时候。edit_file 的设计是 old_string 必须**恰好出现一次**——找不到报错、出现多次也报错（"请扩大上下文让它唯一，或改用 write_file 整体重写"）。我本想实测"多处匹配"的报错路径，让它把 README 里的 mini-coder 改成 MINI-CODER——结果它自己挑了唯一出现的那行标题 `# mini-coder` 去替换，**主动绕开了歧义**，我的测试用例直接落空，最后反而是模型反问我："是将所有 mini-coder 都改大写，还是只替换特定位置？"

想逼出歧义报错，得让它去替换正文里反复出现的普通词。模型比测试用例预想的聪明——这在后面还会反复出现。

## 五、Ctrl+C 侦探故事第二集：软约束挡不住的

上篇第六节讲过一个 Ctrl+C 的侦探故事（生模式/熟模式之谜）。这篇又攒了一集，而且这集的主题更大：**提示词和程序，到底哪个说了算？**

### 前情：中断之后，模型该不该失忆？

先说一个更早发现的问题。agent 干活的时候按 Ctrl+C，请求被打断——那这一轮干到一半的任务，历史里还留不留？

v0.3 的实现是：整轮回滚，当作没发生过。听起来干净，实测立刻翻车：我先说了个暗号"会飞的猫"，然后一个任务干到一半打断它，再追问"我们刚才在干什么"——模型诚实回答它没见过这个提问。**用户亲手打断的回合，进度凭空消失，"继续"也无从接起**。

复盘后发现根本不冲突：Ctrl+C 打断的只是模型的网络请求，而打断那一刻的历史恰好总是协议合法的（要么停在"提问还没答"，要么停在"工具结果刚回填、模型还没接话"）。于是修正为：**真错误（网络断了）才回滚；用户中断保留进度**。修完实测，被中断的"会飞的猫"之后追问，模型准确复述；任务被打断后说"继续"，它从中断点接起，弹窗、执行、自查、汇报一气呵成；我甚至把文件名敲错成 hell2.txt，它对着"文件不存在"的报错自己纠正了。

中断不丢上下文——上篇聊聊天时的体验细节，到了 agent 场景成了关键能力。记住这个，下面这集的主角马上要用到它。

### 第一幕：那行 n 是谁打的？

确认弹窗挂起的时候按 Ctrl+C，应该是什么意思？难点是技术性的：终端在熟模式下，^C 是进程级信号，它和"挂起中的确认输入"之间**没有任何通信通道**——信号处理器没法直接让那个等待中的弹窗结束。

我用了个巧门：信号处理器里执行 `rl.write("n\n")`，**模拟用户敲了个 n**，挂起的确认自然按"拒绝"结算，绕开了和 readline 内部状态的搏斗。

能跑，但实测第一轮就露馅。用户按的是 Ctrl+C，屏幕上出现的却是一个干干净净的 `n`，然后是"（已拒绝）"。用户原话：

> 你看起来是我手输的n，但其实是我ctrl c后就自动输入了一个n

用户自己都分不清那行 n 是谁打的——**结算手段冒充了用户行为**。修法：检测到这次 n 是合成的，就把回显那行用 ANSI 控制符上移、清除、重写成：

```
（Ctrl+C —— 本次操作已中止，视为拒绝）
```

同时给下游一个独立的"取消"标志，不再靠"输入内容是 n"来反推真相。这一课记下来：**凡是模拟输入结算的路径，要么改写账面，要么带上真相标志，别让手段冒充行为。**

### 第二幕：提示词说"不要重试"，它照样重试

显示修好了，我以为完了。但第二个缺陷更深：模型收到的喂回消息，和手敲 n 时一模一样——"用户拒绝了这次操作"。于是它把 Ctrl+C 当成了普通的"不"，回你一句"你确定要覆盖吗？如果确定，我会重新执行写入"。

可 Ctrl+C 的意图明明是**停下**，不是"再问我一遍"。

第一轮修正走的是软路线：给 Ctrl+C 的喂回写一条专门的消息（逐字）：

> 用户在确认弹窗按了 Ctrl+C，中止了这次操作（视为拒绝）。不要再次发起同样的操作，等待用户的新指示。

白纸黑字写明"不要再次发起同样的操作"。实测：

```
> 将hello.txt中的内容修改为大脸猫爱吃鱼，小小老鼠爱吃米
⚙ edit_file 弹窗 → Ctrl+C
（Ctrl+C —— 本次操作已中止，视为拒绝）
 ⚙ write_file(同样内容)          ← 模型自发改用另一个工具，重试了同样的操作！
（Ctrl+C —— 本次操作已中止，视为拒绝）
模型："如果你确认要修改，请告诉我，我会再次尝试写入。"
```

**提示词明说"不要重试"，它照样重试**——甚至换了把刀（edit 被拒就改 write_file），把"换一种方案"的引导用在了错误的地方。顺带说，system prompt 里本来就写着"操作被拒绝时不要原样重试"，照样没用。

这就是本集的题眼：**软约束（措辞）是建议，模型可以听也可以不听；硬约束（程序侧直接停）才是可靠的。**期望模型"看到提示词就乖乖照做"，就像指望"请勿攀爬"的牌子能拦住一个不明白为什么的人——有时候行，有时候不行，而你偏偏在它不行的场合最需要它行。

### 第三幕：程序说了算

最终修法是把 Ctrl+C 升级成**硬约束**：权限决策从"允许/拒绝"两种变成三种，cancel 不再喂任何可商量的消息——**程序直接结束整个 agent 回合**，模型连发言机会都没有。三种结算放在一起看：

| 按键 | 决策 | 模型收到什么 | 后续 |
|------|------|------------|------|
| `y` | allow | —— | 工具执行 |
| `n` | deny | "不要原样重试，换方案" | 结果喂回，模型换方案（软路线） |
| `Ctrl+C` | cancel | "此操作未执行" + **回合直接结束** | 程序侧停死，进度保留（硬路线） |

```ts
if (decision === "cancel") {
  // 剩余未执行的工具调用按"未执行"补齐回填（保持消息协议成对合法），
  // 然后提前结束回合——进度保留，"继续"能接上
  return { content: "", stopped: "cancelled", ... };
}
```

那个"补齐回填"是协议上的讲究：模型本轮要了三个工具，你只回填了一个的执行结果，历史里就有"没对上号的调用"——下次请求可能直接报错。所以中止时把没执行的调用也补上"此操作未执行"的结果，历史永远合法。前情提要里"中断时刻的历史总是协议合法"这个结论，在这里靠主动补齐来维持。

修完第三轮实测：弹窗 Ctrl+C → 屏幕出现中止提示 → **模型没有任何后续动作**。回合干净停住，进度在历史里，说"继续"能接上。用户记录里的原话就四个字：**"这回对了"**。

回头再看这一集：同一个需求（用户想停下），提示词挡不住，喂回措辞挡不住，最后是程序里的一行 `return` 挡住的。调研四个同类实现时记过一条："没有一家有权限/审批机制——Claude Code 的权限确认是产品与玩具的分水岭。"现在你知道这个分水岭是什么做的了：不是更聪明的提示词，是**不经过模型的程序逻辑**。

## 六、账单时刻：读文件的钱花在哪

上篇第七节有个 2427 的账单时刻。这篇有一个更大的，而且这次的账多了一笔新的构成。

最后一轮验收我切到 Anthropic 通道，跑了四个任务：读一个 5169 行的大文件、汇总它、改两个小文件。结束后 `/usage`：

```
本会话累计 4 轮有账：输入 18134 + 输出 1347 tokens
```

18134 的输入。拆开看很有意思：那个 5169 行的文件被读进来时被截断成前 400 行（为什么截断，第七节说），约 5~6K tokens。它们进了历史之后——还记得吗，历史每轮全量重发——**后续每一轮请求都原样重付这 5~6K**。四轮请求的历史规模画出来是这样：

```
轮1  历史 ~1K ──▶ 付 1K        （纯提问）
轮2  历史 ~6K ──▶ 付 6K        ◀── 文件内容从这里住进历史
轮3  历史 ~7K ──▶ 付 7K        （同一份文件，再付一次）
轮4  历史 ~8K ──▶ 付 8K        （还是它）
                            合计 ≈ 18K，和 18134 严丝合缝
```

**同一个文件的内容，被付费了三次，之后每聊一轮再付一次，直到 /clear。**

一句话总结：**读文件的成本不在读的那一刻，而在它进入历史之后的每一轮。**

把镜头拉远：整个阶段 2 六个验收任务跑完，输入 token 累计 43737——纯聊天是绝不至于此的。文件内容（读到的原文、弹窗 diff）进历史后，历史膨胀的速度比聊天陡峭得多。这就是 Claude Code 为什么会主动"压缩"上下文（compact），也是阶段 4 要正面处理的题目。这里先立此存照。

## 七、意外收获

验收清单跑完之后，测试记录里多出几条"计划外"的观察，每一条都比计划内的更有味道。

**一、模型自发"执行后自检"。**整个阶段没有任何提示或要求，但每次 write_file / edit_file 成功后，模型都会**主动 read_file 把刚写的文件读回来核对一遍**，然后才汇报。没有一行代码或提示词教过它这么做。"做完要检查"是阶段 3 才计划教的东西，它在合适的工具面前自己长出来了——这个现象是下一阶段的引子，先按住不表。

**二、agentic search 涌现。**有一次我故意问"刚才咱们在干什么"——而对话历史里确实没什么线索。它没有说"我不知道"，而是自己 list_files 列目录、read_file 翻 README 和 NOTES，从文件里把上下文找回来汇报给我。Anthropic 那篇官方剖析里有句话："让模型自己翻文件（agentic search）通常优于各种花哨的检索方案，文件系统就是上下文工程。"这次是亲眼看到它自然发生。

**三、模型数不准字符。**让它数 hello2.txt 的字符数：文件实际 52 个字（`read_file` 返回的 bytes=158，52 个汉字 ×3 字节 + 2 个换行，严丝合缝），它报 51。让它介绍自己再数：实际 70 个字符（bytes=188 = 59 个汉字×3 + 11 个 ASCII），它报 54。**LLM 按 token 思考，不按字符思考，数数是它的天生弱项**——而工具结果里那个 bytes 字段每次都对（10 个汉字的文件，30 字节，一分不差）。"数数是工具的活，不是模型的活"，这不就是未来 count 类工具的立项理由吗。

**四、大文件截断被正确消费。**read_file 一次最多读 400 行（防止一个巨型文件塞爆上下文）。那个 5169 行的文件读回来时带着 `truncated: true` 标记，模型的反应堪称教科书：如实向我标注"已截断显示前 400 行"、**只汇总它真正读到的部分**、主动邀请我指定具体需求再查。没有假装读全，没有编造没见过的内容。更漂亮的是，它对着 400 行原始 JSON 自己归纳出了一张按 Controller 分组的接口表——**工具负责提供事实（前 400 行），模型负责产生观点（归纳成表）**，这个分工在这一次交互里同时出现了。

## 八、留给你的八个实验

还是上篇的规矩：下面每个实验我都自己跑过，步骤和观察点都给你。全部做完，这篇的内容就从"读过的"变成"见过的"了。

1. **弹窗三连**：连续三个写文件任务，分别按 y、n、a。重点观察按 n 之后模型的反应——它重试了吗？换方案了吗？还是来问你？
2. **越界**：让它读工作区外面的文件（`../xxx` 或者一个绝对路径）。看报错长什么样，然后看它的**下一步**——从报错里推断出路了吗？
3. **带指示牌的墙**：让它"读一下 .env"再"读一下 .env.example"。两个都该被拦。想一个问题：你会放行 .env.example 吗？为什么？
4. **权限记忆**：按 a 之后 `/clear`，再让它写文件。零确认直执行。这算 feature 还是隐患？重启程序后再试，对比一下。
5. **数数**：让它数某个文件的字符数，再自己用别的方式数一遍，对答案。差多少？`read_file` 返回的 bytes 能帮你反推真相（汉字一个 3 字节）。
6. **大文件**：找个几千行的文件让它读。观察 truncated 标注，看它是如实汇报还是假装读全。
7. **中断与继续**：任务干到一半 Ctrl+C，然后说"继续"。它从哪接上的？再问"我们刚才在干什么"，它翻文件找线索了吗？
8. **演工具**：`/tools off` 后让它"读一下 xxx 文件"。看它把工具调用演成什么样。（这个问题留给第 8 个实验是因为它最烧脑：为什么明知道不会执行，它还是要"演"？）

## 九、下一步

阶段 2 收官。现在的 mini-coder 有了：四个文件工具、自写的 diff、路径防护、y/n/a 权限门、敏感文件闸、以及一套"错误喂回自愈"的行为设计。更重要的是，这一轮实测反复撞见了两个现象——**模型自发执行后自检**、**提示词挡不住它重试**——一个说明模型在合适工具面前自己会长出好习惯，一个说明好习惯不能只靠它自觉。

下一篇（阶段 3）就顺着这两条线走：**反思与计划**。让模型先分析后动手、执行后自检——把它已经自发在做的事，变成显式的工程机制。Anthropic 官方给 Agent 循环的定义是四步：gather context → take action → **verify work** → repeat，我们已经有了前两步。
