# 不用 SDK，手写一个 mini Claude Code（三）：先想后做，是逼出来的，不是教出来的

> 这是 mini-coder 系列的第三篇。上篇结尾留了两条线：一条说模型在合适的工具面前**自己长出了好习惯**（每次写完文件都主动读回核对）；另一条说好习惯**不能指望它自觉**（提示词明说"不要重试"，它照样重试）。这一篇就把这两条线拧成一股：**"先分析后动手、执行后自检"——这两件事，到底该怎么让它稳定发生？**
>
> 这篇的主线是一场完整的实验三幕剧：我先记录了"不教它"时的基线表现，然后试着用提示词教它（失败了，而且失败得非常有信息量），最后把这件事交给了程序。读完全篇你会发现一个贯穿三篇文章的结论浮出水面：**凡是你真正依赖的行为，都别托付给提示词——托付给工具清单和代码。**
>
> 和前两篇一样：面向没正经调过 LLM API 的你，先跑起来再拆解；文中每个数字、每段对话都是我自己跑出来的原始记录（key 一律脱敏成 sk-xxx），可复现、可对照。

---

## 0. 先跑起来（十分钟）

准备两样东西，跟前两篇一样：

1. **Node.js**（20 以上版本），终端里 `node -v` 能看到版本号就行；
2. **一个 LLM API key**——门禁卡，别发群里、别截图、别提交进 git。

```bash
# 1. 拿到代码
git clone https://github.com/vslj/mini-coder.git && cd mini-coder
# 注意：本文上半程的实验用上一版代码（还没有本篇要做的功能，
# 这样你才能亲眼看到"没有机制时"的基线表现）
git checkout v0.3.2

# 2. 安装依赖（零运行时依赖，几秒装完）
pnpm install

# 3. 配置钥匙
cp .env.example .env
# 打开 .env，把 sk-xxx 换成你的真实 key
```

启动后先让它准备四个实验材料（内容跟我当时用的保持一致，方便对照）：

```
> 创建一个hello.txt，内容写"我爱你就像老鼠爱大米"
> 创建一个hello2.txt，内容写一段你对自己的介绍
> 创建一个hello3.txt，写上hello china
> 创建一个hello4.txt，写上hello shanxi
```

四个小任务，顺便热了身。然后是本文的主角任务，原样贴给它：

```
> 把工作区根目录下所有 hello 开头的 .txt 文件合并成一个 合并.md，每个文件一节，一级标题是文件名，正文是文件原文
```

它会自己列目录、读文件、写结果、请你确认。任务本身不难，**但我要请你干一件事：全程盯着它，数一数它有没有在任何一个时刻，先告诉你"我打算怎么干"。**

一个字都没说，对吧？

`⚙ list_files` 冒出来你才知道它在列目录；`⚙ read_file` 一个接一个你才知道它读完了原文；红绿弹窗蹦出来你才知道它要写了。它干得其实不错——但你是**闭着眼睛看完全场**的。干完，它直接一句"已完成"，收工。

记住这个"闭眼看完"的体感，本文就是从它出发的。

## 一、先夸它：这活儿干得其实很专业

把刚才那一轮拆开看，你会发现模型在没有**任何**指导的情况下，展现出了相当标准的工作流。我的原始记录（概括），以及每一轮里"你"的参与度：

```
你发任务 ──▶ ┌ 第1轮  list_files    摸目录（没猜文件名，还正确排除了 deps.txt）
             ├ 第2轮  read_file ×4  一轮并行读四个（上篇讲过：一次点多个菜是常态）
             ├ 第3轮  write_file ─── 弹窗 ◀── 全场你唯一的出场：按了个 y
             └ 第4轮  （无工具调用）  直接汇报"已完成"
```

三个值得点赞的细节：

**它先摸清情况再动手。**它没有猜"工作区里大概有 hello.txt 吧"，而是先 `list_files` 把目录看了一遍。我的目录里当时还有个 `deps.txt`，因为不匹配 hello 前缀，被它正确排除了——它是**看**到的，不是猜的。Anthropic 官方剖析 Agent 循环的四步是：gather context（摸清情况）→ take action（动手）→ verify work（核对）→ repeat。前两步，它无师自通。

**它并行干活。**四个 read_file 挤在同一个请求里要，轮次省了一半——这是模型自带的效率感。

那问题在哪？

## 二、再挑刺：两个消失的东西

### 消失之一：计划

第一个问题你已经亲身体感过了：**全程没向用户亮过一个字的计划**。它不是不会计划——它是把"想"的过程全部闷在自己肚子里，你看到的只有一个个 ⚙ 蹦出来。

这对 30 秒的合并任务无所谓。但设想任务变成"重构这个模块"、"把配置迁移到新格式"——你敢闭着眼睛让它折腾你的代码吗？你对 AI 的信任，很大程度上建立在**看得见**上。Claude Code 真产品里专门有个 Plan Mode（先出计划、你点头、再动手），不是因为它优雅，是因为用户真的需要。

### 消失之二：自检（这个更值得警惕）

上篇说过，阶段 2 验收时有个让我们很惊喜的现象：**每次写完文件，模型都会主动 read_file 读回来核对**，然后再汇报。没有任何提示教过它。

这一次呢？`write_file → {"ok":true}` 之后，**直接汇报"已完成"**。读回核对这个动作，一次都没出现。

同一个模型，同一个端点，隔了一天。这是什么原因？

复盘两次实验的任务差异，我发现了一条规律，画出来一目了然：

```
阶段 2：修改既有文件 ──── 感知风险高（改坏一眼可见）──▶ 每次写完都自发 read_file 复查
阶段 3：新建文件     ──── "我自己刚写的还能不知道？" ──▶ ok:true 后直接交卷
```

**"做完要检查"在它那里是习性，不是策略。**习性跟着风险感知走，松紧随机；策略才是每单必查的规则。而工程上能依赖的只有策略。所以阶段 3 的目标可以精确成一句话：**把"先想后做"和"做完复查"从看运气的习性，变成每次都发生的机制。**

## 三、第一次尝试：写提示词教它（失败了，失败得很有价值）

最顺手的工具当然是提示词——既然它不主动，那就在 system 里白纸黑字要求。我在 system prompt 末尾追加了一句（注意这一句话里其实 packing 了**三条指令**）：

> 接到多步任务时，**先用一两句话向用户说明你的行动计划再动手**；**完成写操作后，读回文件核对结果，再向用户汇报**。

然后跑同一个合并任务。这次的完整原始记录我逐行留着，直接看（工具行原样）：

```
⚙ get_time({})                     ← ？这跟合并文件有什么关系
⚙ list_files({"path":""})
⚙ read_file({"path":"hello.txt"})
⚙ read_file({"path":"hello2.txt"})
⚙ read_file({"path":"hello3.txt"})
⚙ read_file({"path":"hello4.txt"})
⚙ write_file({"path":"合并.md",...})
【新文件】合并.md（11 行）
允许执行 write_file 吗？... y
 → {"ok":true,"path":"合并.md","bytes":298}
⚙ read_file({"path":"合并.md"})     ← 它读回核对了！
[已达 8 轮上限，强制停止——模型可能在工具调用里打转，试试换个问法或 /clear]
```

三条指令的成绩单，一张表看完：

| 指令 | 结果 | 证据 |
|------|------|------|
| 写后读回核对 | ✅ **装上了** | write 成功后它真的 read_file 了 |
| 先亮计划再动手 | ❌ **被无视** | 八次工具调用前后，一句"我打算…"都没有 |
| 核对完再汇报 | 💀 **永远没能执行** | 核对刚做完，撞上轮数上限（下详） |

**装上的是"读回核对"**——对照第二节：这条指令是把一个"它本来偶尔会做"的动作**稳定化**了。**被无视的是"先亮计划"**，**没能执行的是"汇报"**——它核对完，正要开口，撞上了一堵墙。

### 8 = 8：一场机制打架的连环案

看最后一行：8 轮上限，强制停止。这里藏着一笔账，值得你亲手数一遍。

这次 8 次工具调用，**每一次都单独占了一轮**——8 次调用 = 8 轮，**上限刚好被吃满，掐死在"读回核对"和"汇报"之间**。一笔账画在时间轴上：

```
①get_time ②list  ③④⑤⑥ read×4  ⑦write   ⑧读回核对  ⑨汇报
  轮1      轮2      轮3~6      轮7       轮8        ↑
                                         ✂ 8 轮上限在此斩断
                                            "汇报"永远没轮到
```

对照第一节：基线实验里四个 read 是并行的一轮，总共才 4 轮左右就收工。而这次提示词让模型要做的**动作变多了**（读回核对是新增动作），消耗的轮数随之变多——但我程序里的轮数上限还是老的 8（这个默认值从学习期的实验原型一路继承下来，防的是模型在工具调用里打转、烧穿 token）。

**指令在加任务量，预算没跟着动，最后被牺牲的是流程的最后一步。**最讽刺的是那条停止提示语本身："模型可能在工具调用里打转"——**误诊**。它没打转，它每一步都干得中规中矩，它只是慢。守护机制杀死了它本要保护的东西。

顺带一个诚实的备注：这一轮里 get_time 是个毫无必要的开头（问时间跟合并文件有什么关系？），四个 read 这次也是一个一个串行来的——跟基线的并行不一样。**每次运行都有随机性**，单次对比不能下强结论（这是用 LLM 做实验跟传统测试最大的差别）。但有一个事实与随机性无关：**完整的执行记录里，从头到尾没有出现过计划文本。**这一条是确定的。

### 为什么"读回"教得会，"计划"教不会？

两条指令的待遇差别才是这次实验真正的产出。我不敢说知道模型内部怎么权衡的，但结果的模式很清楚：

- "写完读回核对"是**顺路**的——它本来就要在这一轮做事，多调一个工具不改变行为模式；
- "先输出计划再动手"是**要专门停下来**的——在它准备开干的势头前，先插一段不产出任何工具结果的序言。

对模型的习性问题，提示词的"建议"它能听也能不听——而**恰好在最需要它听的场合（开始动手之前），它最不听**。是不是很耳熟？上篇第五集：提示词明说"不要再次发起同样的操作"，它照样重试。那次是"禁止做的事它做了"，这次是"要求做的事它不做"——**同一个结论的正反两面：软约束是建议，不是保证。**

那什么是保证？

## 四、原理：软约束管"知道"，硬约束管"能"

把三篇文章攒的实例摆到一张桌上：

| 场景 | 软约束说了什么 | 模型做了什么 |
|------|--------------|------------|
| 上篇：确认弹窗 Ctrl+C 后 | "不要再次发起同样的操作" | 换了个工具重试同样的操作 |
| 本篇：system 要求先亮计划 | "先用一两句话说明行动计划" | 一个字没说，直接动手 |
| 上篇：拒绝喂回后 | "不要原样重试，换方案" | 换了方案 ✓（听了） |
| 本篇：system 要求写后读回 | "读回文件核对再汇报" | 照做了 ✓（听了） |

看到规律了吗——**软约束有时候管用，而你无法预知它什么时候失效，恰恰在要紧场合失效。**原因在于两类约束作用的位置完全不同：

**软约束作用在模型的"知道"层面。**system prompt、喂回消息，本质都是"发给模型的信息"。信息对行为的影响，取决于模型这次怎么权衡——它有权重、有习性、有随机性，所以结果是概率性的。

**硬约束作用在模型的"能"层面。**上篇的路径防护、权限弹窗、敏感文件闸，加上这次的主角——它们不跟模型商量。两层约束的位置，画成图更直观：

```
            发给模型的每轮请求
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
 ┌──────────────┐      ┌──────────────────┐
 │ 信息层（知道） │      │ 能力层（能）       │
 │ system prompt │      │ 工具清单 schema    │
 │ 喂回消息       │      │ 执行器 / 权限门    │
 │               │      │                  │
 │ ← 软约束在这里 │      │ ← 硬约束在这里动刀 │
 └──────────────┘      └──────────────────┘
  概率性：能听能不听       确定性：没有就是没有
```

用一个餐厅的比方：软约束是菜单上印一行"建议不要点太多"；硬约束是**这道菜根本没印在菜单上**。客人可以无视建议，但他点不到不存在的菜。

这也是为什么本篇的解法不是一句更恳切的提示词，而是让"先想后做"变成模型**唯一能做的事**。下面动手。

## 五、动手：/plan 计划模式

设计目标：用户输入 `/plan <任务>`，程序保证三段式流程——

```
> /plan 把合并.md里的标题都改成二级标题
        │
        ▼
┌─────────────────────┐  自然停  ┌──────────────────────┐
│ ① 只读回合           │───────▶ │ ② 批准框              │
│ 工具表 = 只读子表     │  输出    │ y = 按计划执行         │
│ write/edit 不在菜单上 │  计划    │ 其他 = 放弃            │
└─────────────────────┘         │ Ctrl+C = 中止(不退程序) │
                                └───────────┬──────────┘
                                    ┌───────┼───────┐
                                    y       n      Ctrl+C
                                    │       │        │
                                    ▼       ▼        ▼
                              ③ 执行回合   计划留在   计划未执行
                              全量工具回归  历史等意见
                              照历史里的计划干
```

关键动作只有一个：**计划回合把工具表换成只读子表。**实现总共三个文件动了刀，先看一眼全景，再逐站拆：

```
① 制造点 tools.ts ── readOnlyView()：滤掉一切 needsApproval 的工具
        │
        ▼
② 投放点 repl.ts ── 计划回合递只读表，执行回合还回全量表
        │
        ▼
③ 生效点 agent.ts ── 循环只认表：表里有什么，请求里有什么（一行没改！）
        │
        ▼
④ 兜底   tools.ts ── 真幻觉出写调用 → "未知工具" → 错误喂回自愈
```

### 第 1 站：只读子表（约束的制造点）

```ts
// src/tools.ts
readOnlyView(): ToolRegistry {
  const view = new ToolRegistry();
  for (const t of this.list()) if (!t.needsApproval) view.register(t);
  return view;
}
```

七行。筛选标准是 `needsApproval`——**阶段 2 就埋好的那个标志**。当时它只负责"要不要弹确认框"（写类工具设 true），现在一标志两用：凡是需要用户确认的，就是写类；凡是写类，就不进计划模式的菜单。前一个阶段的基建，成了后一个阶段的承重墙——好的抽象会自己产生复利。

### 第 2 站：投放点（REPL 把哪张表递给哪一回合）

```ts
// src/repl.ts（/plan 命令的处理，简化示意）
const planResult = await agentTurnWithUi(tools.readOnlyView(), PLAN_MODE_SYSTEM);
// ...计划自然停，弹批准框...
if (批准) {
  messages.push({ role: "user", content: "计划已获批准，请按计划执行。" });
  await agentTurnWithUi(tools);   // 执行回合：原表归还，写工具全部回来
}
```

同一个回合函数，喂不同的工具表，就是两种模式。注意原表一个字节都没动——`readOnlyView` 造的是新表，写工具在注册表里好好的，只是这一回合没把它们带在身上。

还有个细节：计划批准后喂给模型的那条 user 消息只有一句"计划已获批准，请按计划执行"——**计划本身早就作为 assistant 消息躺在历史里了**。模型无状态，每一轮全量重发历史，所以执行回合的它，看得见自己许诺过什么。这是"先计划"能被检验的物理基础：**说好的方案就摆在上下文里，做的时候按不按它来，一眼可查。**

### 第 3 站：生效点（agent 主循环——一行都没改）

这是我最想让你注意到的一站：**主循环代码里找不到任何"计划模式"三个字。**

```ts
// src/agent.ts——从阶段 1 原样用到今天
const result = await provider.chat(messages, {
  system,
  tools: tools.schemas(),   // ← 表里有什么，就往请求里放什么
  signal,
});
```

循环不区分模式，它只是忠实地把递进来的工具表翻译成请求。所以当第 2 站递进来的是只读子表时，**发给 API 的 tools 数组里根本没有 write_file 和 edit_file**——模型不是"被禁止调用写工具"，而是**压根不知道世上有写工具**。软硬约束的分水岭在这一行现出原形：提示词是"告诉它别做"，schema 收窄是"让它无从知道"。

### 第 4 站：幻觉兜底（万一它做梦都想写呢）

模型的历史里见过写工具（执行回合的往返），万一它在计划回合凭记忆"演"出一个 write_file 调用呢？看执行器：

```ts
// src/tools.ts——阶段 1 就有的代码
async execute(name, args) {
  const tool = this.tools.get(name);
  if (!tool) {
    return { ok: false, content: JSON.stringify({ error: `未知工具: ${name}` }) };
  }
  ...
}
```

表里没有 → "未知工具" → 错误喂回 → 模型自愈（上篇第四节的老机制接住了新情况）。三重保险齐了：**schema 里没有（主体）→ 调了也查无此工具（兜底）→ 真漏网的写操作还有权限门把关（阶段 2 的老闸）**。

你发现没有，这四站里**没有一处是"拦截模型的写请求"**。硬约束的精髓是**少给，而不是多拦**。拦，是要跟模型斗智斗勇的——上篇它替考绝对路径、优雅绕开歧义报错，你永远拦不完它的新路数；而"少给"没有对抗，菜单上没有就是没有。

### 补一刀：轮数预算的校准

第三节那场"8 = 8 误杀"的账不能白算。轮数上限的本意是防打转，但它数的只是"轮数"，并不知道模型是打转还是正常干活。指令加了工作量，预算不跟着走，健康流程就死在汇报前。所以：

```ts
// src/agent.ts
/** 轮数上限，默认 16。阶段 3 实验②的教训：默认 8 会把健康的
 *  "摸目录→逐个读→写→读回核对→汇报"流程掐死在汇报前…… */
maxRounds?: number;
```

8 改 16，注释里把案例写明。这个改法很朴素，但它背后的原则值得记：**上限的尺寸要跟着指令要求的工作量走，不是越小越安全。**

另外，批准框的 Ctrl+C 处理原样复用了上篇第二集的巧门（信号处理器里合成一个 n 让挂起的输入按"放弃"结算，再把回显行 ANSI 改写成"Ctrl+C —— 计划未执行"）——上篇踩过的坑，这里一行没多踩。工程上的坑，踩一次就该变成一块地基。

## 六、验收：四个分支，一个不能少

机制好不好，实测说了算。`git checkout v0.4`（或直接用 master），重启 `pnpm dev`，横幅应该是 **mini-coder v0.4.0**。我按四个分支各跑了一遍，总成绩单：

| 分支 | 操作 | 结果 | 判定 |
|------|------|------|------|
| 主路径 | 计划出来按 y | 执行严格照计划：4 次 edit 与计划一一对应 → 读回核对 → 逐条汇报 | ✅ |
| n | 计划出来按 n | 计划留在历史，模型等修改意见，不擅动 | ✅ |
| 批准框 Ctrl+C | 计划出来按 ^C | "计划未执行"，程序不退 | ✅ |
| 硬约束本身 | 观察全部 4 次计划回合 | 零写类调用——菜单上根本没有那道菜 | ✅ |

**分支一：主路径（最要紧的验收）。**

```
> /plan 把合并.md 里的标题都改成二级标题
〔计划模式：只读工具可用——先摸上下文，再给计划〕
⚙ read_file({"path":"合并.md"}) → ...
计划如下：
**目标**：将"合并.md"文件中的所有一级标题（#）改为二级标题（##）
**执行步骤**：
1. 使用edit_file工具将每个一级标题替换为对应的二级标题（共 4 处）
2. 读回文件确认修改结果
3. 向用户报告完成情况
**风险控制**：逐个替换确保精确匹配，避免误修改其他内容。
按此计划执行？(y=按计划执行 / 其他=放弃) y
〔执行模式：全量工具可用〕
⚙ edit_file(# hello.txt → ## hello.txt)   (+1 / -1 行)  弹窗 y → ok
⚙ edit_file(# hello2.txt → ## hello2.txt) (+1 / -1 行)  弹窗 y → ok
⚙ edit_file(# hello3.txt → ## hello3.txt) (+1 / -1 行)  弹窗 y → ok
⚙ edit_file(# hello4.txt → ## hello4.txt) (+1 / -1 行)  弹窗 y → ok
⚙ read_file({"path":"合并.md"})            ← 计划第 2 步：读回核对
已完成修改。……（逐条汇报四处改动）          ← 计划第 3 步：汇报
```

三个"先想后做"的标志同时在场：**计划先于一切动作出现**；**执行严格照计划走**——四条替换一一对应，一步没跳、一步没加；**写完读回、逐条汇报**——计划里写了第 2、3 步，执行段就兑现了第 2、3 步。第三节提示词教不会的事，硬约束一装就灵。

对比一下轮数：执行回合五、六轮收工，16 的预算余量充足——8 = 8 的惨案没有重演。

**分支二：n（不批准）。**计划出来按 n：计划保留在历史里，模型收到"未获批准"，安静等你提修改意见，不擅自动手。

**分支三：批准框 Ctrl+C。**屏幕出现"（Ctrl+C —— 计划未执行）"，程序不退出——上篇 v0.3.2 修出来的语义，在新弹窗上原样成立。

**分支四（贯穿每次）：计划模式零写类调用。**四次计划回合，没有出现过一次写类工具的影子。

### 三个意外收获

每次验收都会捡到计划外的观察，这次的三条一条比一条有味道。

**一、"根本不用做"也是先想后做的产出。**我拿合并任务重跑了一次 /plan——但 合并.md 上次已经建好了。它读完四个 hello 文件后，**多读了一步：把 合并.md 也读了**，然后计划的内容是：

> 基于对工作区的检查，我发现目标文件 `合并.md` 已经存在，并且内容完全符合要求……**因此，无需进行任何修改**。任务已经完成。

对照一下第一节的基线实验：那时模型对已存在的目标文件毫无察觉，直接重写了一遍。**计划模式把"任务是否已经完成"的检测，提前到了动手之前。**"先分析后动手"的价值不只是防错，还包括发现"这活儿根本不用干"——这是提示词时代从没出现过的行为。

**二、模式的边界画在 system 里，画不进历史里。**主路径批准执行后，模型开口第一句是"在计划模式下，我无法执行写入操作"——明明已经切到执行模式了。原因：计划模式的 system 补充段只作用于计划那一个回合，但计划回合的言行留在了历史里，继续带偏执行回合的自我认知。没造成行为错误（它确实没乱写），但暴露了一个真原理：**每回合现配的是 system，抹不掉的是历史。**多模式 Agent 的上下文设计要预留这一手。

**三、阶段 0 的地基，在 agent 战场第一次开火。**主路径验收进行到一半，两次 edit 之间，终端冒出一行：

```
[chat] 网络错误，1123ms 后重试（第 1/3 次）
```

然后一切照旧。1123ms——和上篇地基阶段实测的 1405ms、1114ms 是同一条指数退避曲线。网络抖了一下，重试层自己缓过来，模型和用户都没被打断，任务继续。**三个月前给纯聊天修的重试，三个月后在工具循环里无声地兜底**——地基工程的回报经常是这样：平时看不见，出事时不需要你。

## 七、留给你的八个实验

老规矩：下面每个实验我都自己跑过，步骤和观察点都给你。做完，这篇的内容就从"读过的"变成"见过的"了。

1. **复现"闭眼看全场"**：用 v0.3.2 跑第 0 节的合并任务，数一数它输出过几个字的计划。然后想想：如果这个任务是"重构你项目的核心模块"，你敢让它直接开始吗？
2. **自检的消失与出现**：同一个会话里，先让它新建一个文件（随便写点什么），再让它修改一个既有文件。观察哪种任务之后它自发 read_file 复查了？"风险感知"假设成立吗？
3. **亲手装一次软约束**：往 `src/cli.ts` 的 system 里加上第三节那句提示词，跑合并任务。它输出计划了吗？（别期望复现我的结果一字不差——每次运行都有随机性，但"计划文本缺失"这个方向是稳定的。）
4. **数轮数**：跑任何一个多步任务，数 ⚙ 行数和最终轮数。如果上限是 8，它会在哪一步死？上限改成 4 呢？（改 `src/agent.ts` 的 maxRounds 默认值。）
5. **主路径**：用 v0.4 跑一个 `/plan` 任务，批准它。逐条对照：计划里的每一步，执行段都兑现了吗？有没有做了计划外的事？
6. **n 分支**：批准框按 n，然后提一条修改意见（比如"分两步做"）。看它怎么在原计划的基础上调整——计划在历史里，它改起来是不是有据可依？
7. **Ctrl+C 分支**：计划出来后按 Ctrl+C。程序退出没？历史里还留着什么？（可以接着问它"刚才的计划是什么"验证。）
8. **"无需修改"挑战**：先让 mini-coder 完成一个小任务，然后**原样再 /plan 一遍同样的任务**。它发现活儿已经干完了吗？这一步是"先分析后动手"价值的试金石。
