# 不用 SDK，手写一个 mini Claude Code（四）：模型没有记忆，账单替它记

> 这是 mini-coder 系列的第四篇，也是最后一篇。上篇结尾留了一个钩子：阶段 2 六个任务，输入 token 累计 43737——文件内容进历史后，每一轮都全量重付。而 Anthropic 四步循环（gather context → take action → verify work → repeat）里，repeat 恰恰是最烧钱的一步：**模型没有记忆，你聊过的每一句话，下一轮都要原样重发一遍、重付一遍钱。**
>
> 这一篇就正面接下这笔账：先把它**量**出来（重发税实测 13 倍），看肥历史除了贵还会让模型变**笨**（退化实录 + 一场取证翻案），然后给 mini-coder 装上压缩机制 `/compact`——验收时设计被实测两次打穿，一次当场修掉、一次留给你，都原样记录。最后顺手做一次腐烂重构、打 tag 收官。
>
> 和前三篇一样：面向没正经调过 LLM API 的你，先跑起来再拆解；文中每个数字、每段对话都是我自己跑出来的原始记录（key 一律脱敏成 sk-xxx），可复现、可对照。

---

## 0. 先跑起来（十分钟）

准备两样东西，跟前几篇一样：

1. **Node.js**（20 以上版本），终端里 `node -v` 能看到版本号就行；
2. **一个 LLM API key**——门禁卡，别发群里、别截图、别提交进 git。

```bash
# 1. 拿到代码
git clone https://github.com/vslj/mini-coder.git && cd mini-coder
# 本篇上半程的实验用上一版代码（还没有 /compact），
# 这样你才能亲眼看到"没有压缩机制时"的账单长什么样
git checkout v0.4

# 2. 安装依赖（零运行时依赖，几秒装完）
pnpm install

# 3. 配置钥匙
cp .env.example .env
# 打开 .env，把 sk-xxx 换成你的真实 key
```

> 计量注意：`/usage` 显示的真实账来自端点返回的 usage。Anthropic 原生通道（含 MiMo 的 `/anthropic` 端点）流式也会回 usage；OpenAI 兼容通道下 MiMo 流式不给——数字为空属正常。做本篇的计量实验，请用给 usage 的通道。

启动后，按下面三步做一组实验。**每做完一步，敲一次 `/usage`，把两个数字记下来。**

**A. 一条依赖链。**让它连做五个互相依赖的小笔记文件，一个接一个，后面的要在前面基础上追加：

```
> 创建 note1.txt，写一段 80 字左右的自我介绍
> 创建 note2.txt：在 note1 的基础上，引用它的内容并加上今天的日期
> 创建 note3.txt：在 note2 的基础上追加一段读后感
> 创建 note4.txt：在 note3 的基础上追加一条待办
> 创建 note5.txt：在 note4 的基础上写一句总结
```

**B. 喂一个大文件。**让它读一个几百行的文件（我当时用的是系列第 1 篇博客的文稿，287 行）：

```
> 读一下 blog/01-不用SDK手写mini-coder-地基篇.md，总结它讲了什么
```

**C. 一个极短的问题。**

```
> 第一个任务是什么？
```

三步做完，我的 `/usage` 账单长这样：

| 步骤 | 这一步干了什么 | 累计输入 tokens | 相比上一步 |
|------|--------------|----------------|-----------|
| A | 五文件依赖链 | 20444 | — |
| B | 读进一个 287 行的文件 | 31860 | **+11416** |
| C | 追问，新输入只有十几个字 | 40491 | **+8631** |

盯住最后一行：**新说的话只有十几个字，代价却是 8631 个 token。**多出来的几乎全是 B 步进历史的那份 287 行文件——它还躺在历史里，每一轮都要重新付一遍。

记住这三个数字，本文就从这个 +8631 开始。

## 一、重发税：历史线性涨，账单平方涨

为什么十几个字的问题要花八千个 token？把模型的工作方式画出来就明白了：

```
messages 数组（你养的记忆）          每一轮发给 API 的内容
┌──────────────────────┐
│ 第1轮 问↔答           │ ──▶ 第1轮请求  [第1轮]
│ 第2轮 问↔答           │ ──▶ 第2轮请求  [第1轮 第2轮]
│ 第3轮 问↔答+工具结果   │ ──▶ 第3轮请求  [第1轮 第2轮 第3轮]
│ ……                   │      ……
└──────────────────────┘
  长度线性增长              账单 = 第1轮+第1、2轮+第1、2、3轮…
                              = 全部历史 × 轮数/2（平方级）
```

这是 M1（系列的起点）就讲过的核心观察，这是它第三次在现场复现，而且最狠：**历史里躺进一个大文件后，之后每一轮的输入地板，就是全部旧账。**这多收的部分，我管它叫**重发税**。

重发税到底有多重？后面做压缩验收的那个晚上，`/usage` 拍下了一张更夸张的标本——同一时刻的两个数字并排：

```
会话累计输入 447919 tokens；当前历史估算 ≈33340 tokens
（两本账：真实账看端点脸色，估算账自己算，压缩决策只认后者）
```

**当前历史 33340，会话累计 447919——13 倍的差就是重发税。**历史是线性涨的，账单是平方涨的；待会儿的压缩砍的是前者，省的是后者。

补一句真产品的对照，免得你拿着这个 13 倍去吓自己：Claude Code 这类真产品里还有**提示词缓存**这一层——重发的历史里命中缓存的部分按大幅折扣计费，税实际打了折。但前提是你走的是自家的通道；自己接的第三方端点没有缓存时，税是全额缴的。mini-coder 教学不实现缓存，但这层认知值得带上：**重发是绕不开的，能优化的空间有三层——历史别太长（本文主角）、缓存打折（平台能力）、输出别太啰嗦。**

## 二、肥历史的第二宗罪：不是贵，是笨

贵只是第一宗罪。实验 A 的那条链上，同一个回合里模型还交出了一份"退化三连"的原始记录：

1. 调出了一个叫 `...` 的工具——`⚙ ...({})`，一个占位符式的幻觉调用；
2. `edit_file` 的 old_string 里混进了它幻觉出来的"对话记录"片段（把 `[思考] 用户要求……` 这种模板语法当成了文件内容）；
3. 一项复制任务只复制了部分内容就落盘，而且没向用户声明。

对照阶段 2 的实验：同模型、同端点，瘦上下文时模型对截断信号消费得妥妥帖帖。**上下文管理不只是省钱，还是保质量。**

退化第 3 条当时我归因为"模型无视截断信号"——后来验收时取证，**翻案了**。翻案过程值得完整看一遍，因为它是"怎么给模型行为定罪"的一堂课。

任务：让它把 blog/02 的文稿复制到一个新文件。两次独立会话，都停在**几乎相同的位置**（142 行上下，6676 和 6643 字节）。第一次我信了模型的事后解释："文件里的 `<tool_call>` 示例被系统误当成工具调用导致截断"——听起来有理有据。

验收时我把截断的文件翻到最底部取证：

```
    ...(代码块中间)
<parameter=path>pnpm-lock.yaml   ← 到此戛然而止
```

**停在代码块中间、停在一个参数的中间**——这是机械截断的铁证，不是任何"聪明地绕开"能形成的形状。真凶是另一头：把 ≈27KB 的文件内容让它"念"进 write_file，撞上了输出端的硬上限 **MAX_TOKENS=4096**（思维链和正文一起算），截断处的 JSON 被服务端救成可解析的形状照常送达，write_file 照常落盘。模型那句"被系统误当"的解释，是**一本正经虚构的**。

这场翻案留下两条教训：

1. **"搬运文件"这类活，根本不该经过模型的生成通道**——模型应该是调度员，不是复印机（这也是 Bash/cp 类工具存在的理由）；
2. **模型的自我解释 ≠ 真实原因**。它不是在撒谎，它只是没有对自己行为的取证权限——归因要靠证据（截断位置、字节数、复现），不靠口供。

## 三、上限的两种死法（顺手缝合两处漏包的伤口）

肥历史还有第三宗罪：容易把服务打挂。同一个晚上，实验撞上了两条不同形状的"死"：

```
同一个故障域，两条路径：

① 流式响应中途断线
   fetch() 成功 ──▶ 响应体读到一半 undici 裸抛 TypeError: terminated
                ──▶ 不是 ProviderError → 重试层放行，没重试
                ──▶ [意外错误] + 内部栈刷屏 + 你的提问被吞

② HTTP 500 连吃三次
   ──▶ 结构化 ProviderError(http 500)
   ──▶ [chat] HTTP 500，1086ms 后重试（第 1/3 次）→ 2s → 4s
   ──▶ 扛过 7 秒窗口后放弃：干净报错 + 提问干净撤回
```

②走的是地基篇修好的那条设计过的路：结构化错误、指数退避、干净收场。①暴露了一个**没罩住的伤口**——错误的包装只罩住了 `fetch()` 调用本身（连接建立、发请求），**响应体读到一半**断线时，undici 从 body 读取循环里裸抛的 `TypeError` 直接穿透了所有防线。修法不复杂：body 消费阶段也包进同一层 network 包装：

```ts
// src/providers/*.ts——响应体消费阶段补上同层包装
} catch (e) {
  if (opts?.signal?.aborted) throw e;   // Ctrl+C 是用户主动中止，别误判成网络错误
  if (e instanceof ProviderError) throw e; // 协议错误原样放行
  throw new ProviderError("network", `网络错误: 响应体读取中断: ${msg}`);
}
```

同一个月还查出一处同科的伤口：**preview 路径绕过了工具错误的包装。**权限弹窗前程序会调 `tool.preview()` 生成"改动预览"，edit 的 preview 内部要做替换计算——old_string 匹配不上就在这里抛错。同一句"找不到要替换的文本"，从执行器里抛会被包装成 `{error}` 喂回给模型自愈（阶段 2 的老设计），从 preview 里抛就直接炸掉整个回合：历史回滚、内部栈刷屏、你的提问被吞。最扎心的是接口注释里明明写着"预览生成失败不算错误，返回 undefined 就行"——**设计意图在，实现漏了**，而且阶段 2 的六场景验收恰好没覆盖"preview 抛异常"这个分支。修法七行：

```ts
// src/agent.ts——权限门处，预览失败按"无预览"兜底
let preview: string | undefined;
try { preview = tool.preview?.(call.args); } catch { preview = undefined; }
```

这个修复的验收还附带一段斗智，值得原样讲给你：我让它"把 biubiu.txt 里的 goodbye 改成 byebye"——想踩报错路径。结果它先 read 了一遍文件，发现没有目标文本，**嘴上回答"文件里没有这个内容"，根本不调 edit_file**。模型比预想聪明，想让它踩报错路径，得掐掉它的自查本能：

```
> 不要读文件，直接用 edit_file 工具把 biubiu.txt 里的 hi there 改成 bye there
(没有改动预览)          ← preview 抛异常，按无预览兜底（修复生效的第一手证据）
允许执行 edit_file 吗？(y/n/a) y
⚙ edit_file(...) ✗ 找不到要替换的文本     ← 包装后的错误，喂回模型
模型：看来文件里没有这段内容，我先读一下文件确认……  ← 平静自愈，回合活着
```

对照修复前的同款错误：`[意外错误]` + 内部栈 + 回合回滚 + 提问被吞。**同一个错误，两种命运，差的只是一层 try/catch 的归属。**

## 四、动手：/compact，给记忆减负

账量完了，死法看过了，该装机制了。思路来自一个朴素的事实：**messages 数组是你自己的**——模型无状态，"记忆"不过是客户端维护的文本数组，数组是自己的，就能改。压缩就是把数组里又老又肥的部分，换成一份简报。

### 4.1 双轨计量：两本账

动手之前先解决"什么时候该压"——得先能知道历史有多肥。这里有本**量纲课**：验收时估算账和真实账首次同屏，"输入累计 20782 vs 估算 1561"，乍一看吓死人。其实不是估算错了，是**两把尺子量的不是同一个东西**：

- **真实账**（端点 usage）：累计口径——每个回合每一轮请求的输入之和，含每一轮重发的历史；
- **估算账**（自己数）：单次口径——当前这个 messages 数组，发一次请求会有多肥。

可比的时刻是"单轮请求"：C 步追问的真实输入 8518（40358 − 31840）vs 估算 7937，误差 ~7%，差额 ≈ system prompt + 工具 schema 这两块固定开销（估算器刻意没算它们）。**粗账够决策用**——阈值判断只需要知道"6 万还是 8 万"，差 10% 无所谓。

估算器本身就是十几行：

```ts
// src/compact.ts——CJK 字 ≈1 token/字，其他字符 ≈4 字符/token
export function estimateTokens(text: string): number {
  let cjk = 0, other = 0;
  for (const ch of text) {
    const cp = ch.codePointAt(0)!;
    if (cp >= 0x4e00 && cp <= 0x9fff) cjk++;
    else other++;
  }
  return cjk + Math.ceil(other / 4);
}
```

那为什么决策用估算、不用真实账？因为**真实账看端点脸色**——MiMo 的 OpenAI 兼容通道流式不给 usage，账本可能随时是空的。决策不能依赖"端点今天给不给账"，所以触发判断只认估算。两本账各司其职，`/usage` 把它们并排展示（0 节那句带括号说明的输出，就是重构后的它）。

### 4.2 摘要：保什么丢什么，是设计者的决定

压缩的动作是：把切口之前的旧历史发给模型，让它总结成一份不超过 500 字的简报，替换原来的逐条对话。**保什么、丢什么，写死在指令里——这是设计者的决定，不是模型的（M5 最重要的结论）：**

```ts
const COMPACT_PROMPT =
  "请把以上对话历史压缩成一份简报（不超过 500 字），必须包含：\n" +
  "1. 任务目标（含仍在进行中的部分）；\n" +
  "2. 已完成的操作与产出的文件（文件名 + 内容要点）；\n" +
  "3. 未完成的部分与下一步；\n" +
  "4. 用户明确表达过的偏好、约束或纠正。\n" +
  "直接输出简报正文，不要寒暄。";
```

一个容易被忽略的细节：**这份摘要请求刻意不带 tools**。摘要不需要工具说明书；而且历史里全是工具往返时，带上工具清单，模型可能"演"起工具调用来——上篇讲过的诱导现象，在摘要场景同样生效。

### 4.3 尾部：第一次实现，被实测打穿了

光有简报还不够——正在进行的任务，状态全在最近的几轮里，直接说"继续"得能接上。所以压缩后除了简报，**最近的若干回合原样保留**（Claude Code 的 auto-compact 也是这个思路）：

```
压缩前
┌──────────────────────────────────┬────────────────────┐
│  旧历史（第1~N回合，逐条对话）      │ 尾部：最近几个回合   │
└──────────────────────────────────┴────────────────────┘
              │ 让模型总结成 ≤500 字简报        │
              ▼                              │ 原样保留
┌──────────┬──────────────────────────────────┴────────┐
│ 〔历史已压缩〕│ 尾部回合原样保留                          │
│  简报       │  ← 切口必须落在 user 消息边界（4.4）        │
└──────────┴───────────────────────────────────────────┘
```

第一版尾部策略很直觉：**按条数**——保留最近 2 轮。自动压缩首触发，当场暴露问题：

```
〔历史估算 ≈62486 tokens，超过阈值 60000——自动压缩〕
〔历史已压缩：被替换部分 ≈33340 → 摘要+保留段 ≈29569 tokens……〕
```

报告乍看像"压了个寂寞"——33340 → 29569，只省 3800？先别急着下结论，这笔账要拆开算：**总数 62486 = 被替换的旧历史 33340 + 原样保留的尾巴 29146**。旧历史确实压成了一份几百 token 的简报——**压缩本身干得不错，问题全在尾巴上**：按"最近 2 轮"留尾，尾巴恰好是刚塞进去的两次大文件读取（每个 read 结果在历史里 ≈1.1 万 token），**2.9 万 token 原样留在历史里**，之后每一轮的重发税一分不少。**刀落下时肉都在尾巴上**——简报省下的空间，被超载的尾巴吃掉一大半。

顺带记一笔报告设计的教训："被替换部分 A → 摘要+保留段 B"这个口径，A 不含尾巴、B 含尾巴，乍看之下 A−B 像"节省量"，实际上什么都不是——**报告的读法差点骗了我**。

按条数保留在内容体积方差小的聊天场景够用；但 agent 的历史里，大工具结果是常态，**这类策略必须换算成体积口径**。

修正：尾部按**体积封顶**（8000 tokens 上限），从最后一个回合往前扫，装得下的最早回合边界就是切口；**最后一个回合无论如何保住**——正在进行的任务状态全在里面，连续性优先于水位：

```ts
// src/compact.ts——找切口：从后往前积累只会变大，一超限即停
let cut: number | undefined;
for (let k = userTurns.length - 1; k >= 0; k--) {
  const start = userTurns[k]!;
  if (estimateHistory(messages.slice(start)) <= KEEP_TAIL_TOKEN_CAP) cut = start;
  else break;
}
// 一个都装不下（最后回合独自超限）：仍然保住它——连续性优先于水位
if (cut === undefined) cut = userTurns[userTurns.length - 1];
```

顺带一提，这个问题在我学习期的 M5 原型里**不可能暴露**——原型里没有大工具结果。设计缺陷要靠真实负载逼出来，这是"先跑起来再拆解"的又一票。

### 4.4 切口：协议合法性靠构造，不靠检查

切历史有一条暗礁：切口位置不能切断工具调用的配对关系。一问一答的历史里，assistant 的 tool_calls 和紧随其后的工具结果是一对，**切口若落在这对中间，发给 OpenAI 的是孤儿 tool_call_id，发给 Anthropic 的是没有 tool_use 对应的 tool_result——两边协议都直接拒绝**。

mini-coder 的解法是不检查、只构造：**切口永远落在 user 消息边界**（保留段从一条 user 消息开始到末尾），配对关系从结构上就永远不会被拦腰切断。这与阶段 2 中断语义的设计一脉相承：**协议合法性靠构造不靠检查。**

### 4.5 验收：22813 → 9900，"简报质感"一次成像

机制装好，实测说话。手动 `/compact`，实测被替换 22813 → 9900：

```
> /compact
〔压缩中——正在请求模型总结旧历史……〕
〔历史已压缩：被替换部分 ≈22813 → 摘要+保留段 ≈9900 tokens……〕
```

**−56%。**但省了多少只是半张答卷，另一半是**丢了什么**。压缩后我追问"第一个任务是什么？"——任务结构、文件名、追加方式全部正确；但每句话的**具体内容蒸发了**：压缩前它能精确复述 note1 那条"80 字笔记"的完整要求，压缩后只剩"80 字笔记"四个字。**简报保住了骨架，逐字记忆没有了——"简报质感"与逐字记忆的对比一次成像。**

紧接着验收连续性："在 note5 的基础上做 note6"——模型无缝衔接，而且**主动 read_file(note5) 把全文捞了回来再动手**。这一下把一个重要的分工照清楚了：

```
messages（内存里的数组）──▶ 会话的缓存：可压缩、可丢弃
文件系统（磁盘上的文件）──▶ 持久的上下文：丢了的细节，磁盘上找得回来
```

**文件系统是持久上下文，messages 只是缓存。**这也是为什么"保留尾部 + 主动重读"这个组合是够用的：真正需要逐字精度的内容，让它落盘，随时可捞。

### 4.6 还剩一个病例（留给读者）

体积封顶上线后重开新会话再测一次：总历史 38688，其中最后一个回合就占 16089。切口逻辑从后往前找"装得进 8000"的回合边界——最后一个回合自己就超了，按"无论如何保住"整体幸存。报告：被替换 22599 → 摘要+保留段 16842。压缩本身又干得不错（22599 的旧历史压成几百 token 的简报），但**总水位只降到 16842**——离"简报 + ≤8000 尾巴"的理想水位（≈9000）还高出约 8000，多出来的全在最后回合里，之后每轮继续缴重发税。

与 4.3 那个病例凑成一组：①尾巴是**多个回合**时，体积封顶已治好；②**单个回合内部**的巨无霸工具结果，回合级的切口无能为力——要治它得下更细的刀：把尾部**已完成**的读取类工具结果压成占位符（细节磁盘可找回，4.5 刚验证过），代价是"最后一问若恰好正依赖该内容"会受伤。这个取舍我没有做——**留给你**，这是个非常好的练手机会。

## 五、命令表的腐烂与重构

本篇还有一件小事，小到差点不值得写——但正是这种事最能说明"代码为什么会腐烂"。

mini-coder 的 REPL 命令从阶段 0 的 2 个长到了 9 个（`/exit` `/clear` `/usage` `/provider` `/tools` `/plan` `/compact` `/help`……），分发逻辑是最直觉的 if/else 长链。腐烂的症状有两个：

```
// 旧世界
if (line === "/clear") { ... }
else if (line === "/usage") { ... }
else if (line.startsWith("/plan ")) { ... }
// ……近 80 行分发；
// 另一处：/help 的输出是手写的一份菜单字符串
```

1. **新命令要改两处**：分发段加分支，/help 手工同步菜单——两处不同步，/help 就在向用户撒谎；
2. **80 行的 else 链没有结构**，命令的行为散落在分支里，想看"有哪些命令、各干什么"要通读全链。

重构方案是表分发——每个命令一个对象，/help 从表自动生成：

```ts
// 新世界：单一事实来源
type CommandOutcome = "exit" | "handled" | "fallthrough";
interface Command {
  help: string;                       // 菜单文案就在这里——/help 自动生成
  run(arg: string): CommandOutcome | Promise<CommandOutcome>;
}
const commands: Record<string, Command> = {
  "/compact": { help: "压缩历史（摘要+按体积保留尾部……）", run: async () => { await doCompact(); return "handled"; } },
  "/plan": { help: "<任务> 计划模式（只读侦察→批准→执行）", run: (arg) => { ...; return "fallthrough"; } },
  // ……9 条，一目了然
};
```

两种结局的设计值得说一句：命令要么 `"handled"`（程序自己消化，继续读下一行），要么 `"fallthrough"`（命令只是给对话做了铺垫——比如 `/plan` 设好计划任务后，把它当对话输入交给 agent）。**命令与对话不是两个世界，fallthrough 就是它们之间的桥。**

重构后一条烟测：`/help`（自动菜单与命令表逐条一致）、`/usage`（正常）、`/bogus`（友好报错）、`/exit`（干净退出）。功能没变，但每加一条新命令从"改两处"变成"加一个对象"——**腐烂不是写坏代码造成的，是每次"就改一处"的省事累积出来的。**

## 七、留给你的八个实验

老规矩：下面每个实验我都自己跑过，步骤和观察点都给你。做完，这篇的内容就从"读过的"变成"见过的"了。

1. **复现 token 曲线**：`git checkout v0.4`，跑 0 节的 A/B/C 三步，每步 `/usage`。你的 +8631 和我的不会一字不差（随机性），但"C 步的代价远大于 C 步的新输入"这个方向是稳定的。
2. **拍一张重发税标本**：随便养肥一个会话（多读几个大文件），然后 `/usage` 盯着"累计输入"和"当前历史估算"两个数字——算一算你的倍数。
3. **量纲课**：找一次单轮请求（比如 C 步），用"累计差值"算出它的真实输入，再和"历史估算"比一比。误差落在哪？差额是什么？（提示：system + 工具 schema。）
4. **手动压缩与细节蒸发**：把会话养肥后 `/compact`，先问"第一个任务是什么？"记下答案的颗粒度，再问一个需要逐字细节的问题（比如"note1 的完整要求是什么？"）。感受"简报质感"。
5. **磁盘找回**：压缩后接着说"继续"，盯着它有没有主动 read_file 把细节捞回来。这一步会看到"文件系统是持久上下文"的现场。
6. **自动压缩**：继续往会话里塞大文件直到顶过 60000，看 `〔历史估算 ≈N tokens，超过阈值——自动压缩〕` 出现，再检查压缩报告里"保留段"是否 ≤ 8000（如果它独自超限，你就复现了 4.6 的病例）。
7. **取证练习**：让它把 blog/01 复制到一个新文件，观察截断位置；`/usage` 看输出 token 是否撞上 4096 上限。然后问它"为什么截断了"——**对照你的取证结论，看它的自我解释靠不靠谱。**
8. **给命令表添一条**：照第五节的格式加一条 `/history`（打印 messages 条数），然后 `/help`——看你的新命令**自动**出现在菜单里。这就是表分发的红利。

## 八、收官：四步循环，闭环了

四篇走完，回头对一次账。Anthropic 剖析 Agent 循环的四步，mini-coder 一步一步补齐了：

| 步骤 | 补齐方式 | 出处 |
|------|---------|------|
| gather context | 模型无师自通（先摸目录再动手） | 篇③实验① |
| take action | 工具框架 + 文件工具 + 权限门 | 篇①② |
| verify work | 写后读回自检（从习性变成机制） | 篇③ |
| repeat 的成本 | /compact 压缩 + 体积封顶尾部 | **本篇** |

四篇各自留下的那条主线，也在这里合流：模型无状态（篇①）→ 所以 messages 是你养的记忆（篇①）→ 所以历史是客户端数组、可改（本篇压缩的全部前提）→ 而真正持久的上下文是文件系统（本篇验收）。以及那个贯穿系列、越来越确信的结论——

**凡是你真正依赖的行为，都别托付给概率性的信息层（提示词），要托付给确定性的能力层（工具清单、schema、代码）：计划靠只读子表装上的，读回核对靠提示词稳定下来的，压缩靠改写自己的数组做到的。**

mini-coder v0.5，agent 主循环只有 174 行（外加分篇的文件工具、压缩模块、权限门），零运行时依赖，四篇博客每一步可溯源。它很小，但走完这一遍，"Agent 的核心循环"对你我来说不再是黑盒——**账单会替它记，而账单我们看得懂。**
