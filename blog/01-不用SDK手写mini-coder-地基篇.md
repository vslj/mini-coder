# 不用 SDK，手写一个 mini Claude Code（一）：先把程序跑起来

> 这是 mini-coder 系列的第一篇。这个系列要做的事：**不依赖任何 SDK 和框架**，从裸 HTTP 请求开始，亲手写一个极简版 Claude Code，把"AI 编程助手到底是怎么回事"一层层拆开看。
>
> 这一篇写给谁：会一点编程、平时用 AI 写代码（或者看别人用），但没正经调过 LLM API 的你。不需要你会 TypeScript，代码我都标了注释；需要的是愿意跟着动手——因为这篇的一切设计都围绕一件事：**先让你把程序跑起来，再去解释你刚才看到的每一个现象。**
>
> 全部代码开源，v0.1 已打 tag。文中引用的每个数字、每段对话，都是我自己跑出来的原始记录，可复现。

---

## 0. 先跑起来（十分钟）

先别管原理，我们直接开跑。跑起来之后，你再回头看我讲的东西，每一条都能对上你亲眼见过的现象。

准备两样东西：

1. **Node.js**（20 以上版本）：一个能让 JavaScript 脱离浏览器、直接在你电脑上运行的环境。装完后在终端里输 `node -v` 能看到版本号就行。
2. **一个 LLM API key**：就是"调用 AI 的钥匙"。你去大模型开放平台（我用的是小米 MiMo，用 DeepSeek、智谱、通义都一样）注册后，创建一个 key——长得像一长串以 `sk-` 开头的字符。**它就是门禁卡，谁拿着它谁就能花你账户里的钱，所以别发到群里、别截图、别提交进 git。**

然后三步：

```bash
# 1. 拿到代码（克隆仓库，或直接下载解压）
git clone <仓库地址> && cd mini-coder

# 2. 安装依赖（本系列刻意只用极少工具，几秒就装完）
pnpm install

# 3. 配置钥匙
cp .env.example .env
# 用编辑器打开 .env，把 sk-xxx 换成你的真实 key
```

`.env` 是一个本地配置文件，程序启动时会从这里读你的 key。它已经被加进了 `.gitignore`——git 永远不会把它打包带走。

启动：

```bash
pnpm dev
```

你会看到一段启动信息（模型、接口地址、还有你的 key——只显示 `sk-xxx` 和长度，程序自己也不打印原文，这是安全习惯），然后出现一个提示符：

```
>
```

输一句话试试，比如"用十个字介绍你自己"。你会看到一件可能让你愣一下的事：**先出来一段暗淡的小字，标题是 `[思考]`，然后才是正文**。那个暗淡的部分是模型的思维链——它打草稿的过程。稍后我会解释为什么你能亲眼看到它。

再试试 `/help`，能看到四个命令：`/exit` 退出、`/clear` 清空记忆、`/usage` 查 token 账单、`/provider` 切换协议通道（这个名字现在还神秘，第三节揭晓）。

好，程序在你手上了。接下来我们做六七个实验，把"AI 对话"这件事从玄学变成你看得见的东西。

## 一、你敲的那句话，到底去了哪里？

你在 `>` 后面敲下"你好"，回车。屏幕上一个字一个字往外蹦出回答。

这中间发生了什么？你可能会想：发给了"AI"。但"AI"不是一层云雾——它是一个具体的网络服务，跑在某家公司的服务器上。你的话被程序打包成**一段 JSON 文本**，通过 HTTP 请求（就是浏览器加载网页用的那种协议）发到了 `api.xiaomimimo.com` 这样的地址。

JSON 是什么：一种约定好的文本格式，用花括号和引号来组织数据，人和机器都能读。你发过去的请求长这样（真实请求，一字未改）：

```json
{
  "model": "deepseek-v4-pro",
  "messages": [
    { "role": "system", "content": "You are a helpful assistant." },
    { "role": "user", "content": "你好，用一句话介绍你自己" }
  ],
  "stream": false
}
```

注意这个 `messages`，它是个**数组**——一段对话里所有的话，按顺序排成一列。`system` 是你给模型定的规矩（"你是个乐于助人的助手"），`user` 是你说的话。模型服务器返回的也是 JSON：

```json
{"id":"009db93e-...","model":"deepseek-v4-pro","choices":[{"index":0,"message":{"role":"assistant","content":"你好，我是一个智能助手，致力于用简洁准确的方式帮助你解答问题。","reasoning_content":"我们需要回答用户请求。用户说"你好，用一句话介绍我自己"。需要注意中文。需要一句话介绍自己。……"},"finish_reason":"stop"}],"usage":{"prompt_tokens":95,"completion_tokens":100,"reasoning_tokens":80}}
```

一坨单行，很密，但值得眯着眼读一遍，因为里面有三个宝藏：

**宝藏一：`content` 前面还有个 `reasoning_content`。**回答正文就 20 个字，但 `reasoning_content` 里拖着长长一段"我们需要回答用户请求……需要注意中文……可以。"——这是模型打草稿的过程，也叫**思维链**。你在 `pnpm dev` 里看到的那段暗淡小字，就是它。

**宝藏二：账单。**`usage` 里 `completion_tokens: 100`，其中 `reasoning_tokens: 80`。**80% 的输出 token 花在了你看不见的草稿上。**token 是大模型计费的单位，你可以粗略理解为"半个到一个词"。所以"一句话回答"的真实成本可能是你想象的三四倍——思考是要花钱的。

**宝藏三：`prompt_tokens: 95`。**你刚才那句话撑死 10 个 token，95 哪来的？多出来的部分是协议开销和 system 提示词——发一段话，还有很多"随件费用"。这个伏笔先埋着，第七节有个大数字等它。

## 二、它凭什么记得你上一句？（全场最有意思的一课）

我做验收测试的时候，在同一个会话里把同一个问题问了两遍（"9.11 和 9.9 哪个大？"）。第二遍，模型的回答末尾冒出一句：

> 你是在测试我吗？哈哈，放心，答案不会变的～

它"记得"我问过。对吧？

然后我做了另一个实验。先说一个暗号，模型确认："好的，我记住了！暗号是'莲榴萨披' 🔑"。然后我输入：

```
/clear
(历史已清空)
```

再问"我的暗号是什么"——它一脸茫然，礼貌地解释它不可能知道我的暗号，还热情地猜我是不是想玩游戏。

同一台服务器，同一个模型，前一分钟还信誓旦旦"记住了"。

两个现象放在一起，谜底就出来了，而且它可能是你读完这篇最重要的一个认知：

**模型服务端是无状态的。它没有记忆。"多轮对话"之所以看起来连贯，是因为你的程序每次都把完整的聊天历史重新发一遍。**

- 它"知道"自己被重复提问，因为重发的历史里躺着上一遍的提问——它不是记得，是**每次都重新看一遍全部聊天记录**；
- `/clear` 之所以能让它"失忆"，只是因为程序清空了自己手里那个 messages 数组。四行代码：`messages.length = 0`。

这个认知有个可以直接验证的推论：**记忆是要花钱的**。两轮对话实验，第一轮 `prompt_tokens: 95`，第二轮我把第一轮的问答手动拼回请求里发出去，`prompt_tokens: 123`。多出的 28，就是被重发的历史的价格。先别嫌少——第七节它会滚成一个四位数。

哦对，还有个细节陷阱：`reasoning_content`（那份草稿）**不应该**拼回历史再发出去。这是各家模型的规矩之一——但有意思的是，DeepSeek 的文档这么说了，你带着回传它也照样跑（服务端宽容忽略）。这种"宽容"是危险的，换一家就可能报错。这个坑直接催生了本文第四节的设计。

## 三、一个字一个字往外蹦，是怎么做到的？

回到你跑起来的那个程序。如果不做任何特殊处理，模型会憋到整段话全部生成完，一次性把完整 JSON 甩给你——你可能要盯着屏幕干等十几秒。

但你看到的是打字机效果。这不是特效，是**另一种响应形态**：请求里加一个 `"stream": true`，服务器就不再"攒够了再给"，而是边生成边推送。推送用的格式叫 **SSE**（Server-Sent Events，服务器推送事件）：响应是一长串文本，一行一行地到，每行长这样：

```text
data: {"choices":[{"delta":{"content":null,"reasoning_content":"我们需要"}}]}
data: {"choices":[{"delta":{"content":null,"reasoning_content":"回答"}}]}
data: {"choices":[{"delta":{"content":"是的","reasoning_content":null}}]}
```

每一行是一个 `delta`（增量）——不是全文，是**这次新长出来的那一小块**。你的程序边收边把小块拼起来，拼到哪画到哪。所谓打字机效果，就是"边收边画"这四个字。

我裸眼看原始流的时候，发现了它最有意思的规律——**两种 delta 的接力**：

1. 前面几十行，`content` 全是 `null`，内容全在 `reasoning_content` 上——模型在打草稿，一个词一个词推给你；
2. 某一行开始，`reasoning_content` 变 `null`，`content` 接棒——草稿打完，正文开写；
3. 最后一行 `finish_reason` 从 `null` 落定为 `"stop"`，然后一行字面量的 `data: [DONE]` 收尾。

这就是你启动程序时看到的画面："先暗淡的 `[思考]`，后正文"。那个暗淡小字不是装饰，它就是 `reasoning_content` 的 delta 流——你在等的那几秒里，模型不是卡了，是在打草稿，而且草稿内容你全程可见。花着 80% 的输出 token，你至少能看到钱花哪了。

顺带说清一个常见误会：**流式不省钱，一个 token 都不少收**。它省的是"等待感"——十几秒的干等变成第一秒就有反馈。

## 四、换一家模型服务，代码会怎样？（provider 翻译官）

系列实验的前半程，我用的通道是 DeepSeek；后来换成了小米 MiMo。换通道那天我以为改个网址和 key 就完事了，结果被现实教育了：**每家模型服务说的都是"普通话加自己的方言"**。

正好，MiMo 同时提供两种协议的接口，我把两种都实现了，差异就成了一张现成的对照表：

| | OpenAI 兼容协议 | Anthropic 原生协议 |
|---|---|---|
| system 规矩放哪 | messages 数组的第一条 | 一个独立的顶层参数，不进数组 |
| max_tokens（回复长度上限） | 可以不填 | **必填**，不填直接报错 |
| 钥匙怎么带 | `Authorization: Bearer` 头 | `x-api-key` 头 + `anthropic-version` 头 |
| 思维链在响应的哪 | 私有字段 `reasoning_content` | content 数组里的 `thinking` 块 |
| "说完了"怎么表示 | `finish_reason: "stop"` | `stop_reason: "end_turn"` |
| 流式长什么样 | 清一色 `data:` 行 | 每块带 `event:` 标签的事件流 |

（第一次看这张表只需要带走一句话：**每家不一样，而且碎得超出想象**。具体的以后用到再回来查。）

还有更碎的方言细节，全是我实测撞上的：MiMo 的思维链，在流式响应里排在正文**前面**，在非流式 JSON 里却排在正文**后面**——解析代码不能依赖顺序，只能看类型；流式开头的账单里 `input_tokens: 1`，同一个请求非流式问却是 65——它的流式账单开头那部分不可信。

面对这么碎的差异，正确的做法不是把两种协议的代码搅在一起写，而是先定义一套**自己的中间格式**（程序内部只认这一套），然后每家协议各写一个"翻译官"，把外部方言翻译成中间格式。这个"翻译官"就叫 **provider**：

```ts
// 程序内部的通用格式（只有这么小一点）
interface ChatMessage {
  role: "user" | "assistant";
  content: string;
  reasoning?: string;   // 草稿只用于本轮展示，存历史时只存 content
}

// 每家协议实现同一个接口——OpenAI 一个翻译官，Anthropic 一个翻译官
interface Provider {
  chat(messages, opts?): Promise<ChatResult>;                // 不流式
  chatStream(messages, onEvent, opts?): Promise<ChatResult>; // 流式
}
```

注意 `reasoning?: string` 后面那句注释：**存历史时只存 `content`，草稿不存**。还记得第二节那个坑吗——DeepSeek 说草稿不该回传。与其靠自觉，不如让类型系统堵死这条路：历史里的消息压根装不下草稿这个字段。这就是"你 `/provider anthropic` 一切照旧"的底气——程序的主体只认中间格式，翻译官随便换。

你启动时看到的 `/provider openai` 和 `/provider anthropic`，就是在这两个翻译官之间切换。亲测同一个问题用两个通道问，终端呈现几乎一模一样——**两套完全不同的协议方言，被一层薄薄的抽象抹平了**。

## 五、网断了会怎样？

写程序不能只考虑顺风局。我把 Wi-Fi 关了，然后对着 REPL 问了个问题。终端打出了这些：

```
[chatStream] HTTP undefined，1405ms 后重试（第 1/3 次）
[chatStream] HTTP undefined，2022ms 后重试（第 2/3 次）
[chatStream] HTTP undefined，4326ms 后重试（第 3/3 次）

[provider 错误 network] 网络错误: fetch failed
```

注意三个细节：

1. **它没有立刻放弃，也没有疯狂重试**，而是等 1.4 秒、2 秒、4.3 秒，一次比一次久。这叫**指数退避**：服务器出问题时（比如限流），一窝蜂地立刻重试只会火上浇油；隔一会儿再试，间隔越来越长，是公认的礼貌做法。数字也有讲究：`1秒×2ⁿ + 一点随机抖动`，抖动是防止所有客户端在同一毫秒一起重试。
2. **三次重试都失败后，它干净地报错停手**，没有崩掉整个程序，也没有无限重试烧你的 token。
3. 错误信息分了**种类**：`network`（网没通）、`http`（服务器回了但状态码不对，比如 401 钥匙不对）、`protocol`（服务器回了但内容看不懂）。这个区分很值钱：网络抖动值得再等等；401 重试一百次也没用——钥匙错了就是错了。

（眼尖的你可能注意到日志里有个"HTTP undefined"——那是我第一版的小 bug：网络错误压根没有状态码，我却硬按 HTTP 错误的格式打日志。已修。放在这是想说：调试日志也是代码，一样会犯错。）

## 六、Ctrl+C 之谜（一个 Windows 侦探故事）

这个坑我认为是本篇最值得讲的，因为它完美演示了"文档不会告诉你、只有亲手写才会撞上"是什么意思。

设计目标：回答流到一半时按 Ctrl+C，请求中断、回到提示符，程序不退出。实现完，在 Windows 上一测：**按了没反应**。多按几次，程序突然整个退出。

两头都邪门：该响应的时候没响应，不该退出的时候退出了。排查下来，谜底在终端的最底层。

**正常模式下，Ctrl+C 是一个"信号"**：操作系统专门通知你的程序"用户想中断你"，程序可以接住这个通知自行处理。但 readline（Node.js 用来做命令行输入的工具库）为了实现"一个字符一个字符地读你按键"，会把终端切进一种叫**生模式（raw mode）**的状态——在这个模式下，Ctrl+C 不再是信号，而是**降格成了一个普通字符**（`\x03`），混在按键流里等待程序来读。

问题就出在流式期间：我的程序让 readline"暂停读输入"（防止你的按键和打字机输出搅在一起），结果 Ctrl+C 变成的那个 `\x03` 就滞留在缓冲区里**没人来读**。等回答画完、readline 恢复读输入，积压的 `\x03` 一股脑被处理——这就是"多按几次突然退出"。

修法顺势而出：流式暂停期间，把终端临时切回正常模式，让 Ctrl+C 恢复信号身份，走另一条中断通道；回答画完再切回生模式：

```ts
rl.pause();
process.stdin.setRawMode?.(false);  // 切回正常模式：让 Ctrl+C 重新成为"信号"
// ……流式请求与渲染……
process.stdin.setRawMode?.(true);   // 还原生模式：readline 的行编辑依赖它
rl.resume();
```

修完的实测效果：流到一半按 Ctrl+C，立刻看到 `[已中断]`，回到提示符；更有意思的是，如果中断前已经流出半截正文，程序会把这半截**带着"[回答被用户中断]"的标注存进历史**。我中断了一次"用 JS 写个链表"的回答，然后问"我上一句回答到哪了"，模型精确复述到断在哪一行，还主动问要不要续写。

中断不丢上下文——这对聊天是体验细节，但对后面要写的 Agent（任务干到一半被打断）是关键能力。

## 七、账单时刻：那个 2427

现在兑现第二、三节埋的伏笔。

我把 REPL 的六项验收跑完，最后一项时切到 Anthropic 通道，问了个极短的问题："5.0 和 5.001 哪个大？"——十个字。回答完输入 `/usage`：

```
本会话累计 1 轮有账：输入 2427 + 输出 149 tokens
```

**输入 2427。**一个十个字的问题。

多出来的两千多是什么？是**整个会话的历史**——包括之前那篇几百字的 SSE 与 WebSocket 长文、两遍 9.11、暗号游戏。第二节说过"重发不免费"，第三节说过流式怎么拼增量，现在看它们滚成一个数字：

**对话成本主要由历史长度驱动，你新说的那句话几乎不影响账单。**

这也解释了 Claude Code 为什么会在上下文快满时主动"压缩"（compact）——不是模型嫌长，是每一轮都在为全量历史付钱，长历史就是复利。上下文管理这条线，系列后面专门写一篇。

（一个小注脚：MiMo 的两种协议，流式账单一个给、一个不给——`/usage` 的数字只在 anthropic 分支下增长。这不算 bug，算方言，见第四节。）

## 八、留给你的六个实验

纸上得来终觉浅。下面六个实验，每个都是我自己跑过的，复现步骤给你，观察点也给你。全部做完，本文的内容就从"读过的"变成"见过的"了。

1. **看草稿**：问"9.11 和 9.9 哪个大？"盯着暗淡的 `[思考]`。看完正文后想一下：为什么这么简单的题它还要打稿？（再问一个"帮我写个 JS 链表"感受一下草稿长度。）
2. **失忆**：说一个暗号 → `/clear` → 问暗号。它该装不认识你。
3. **重复提问**：同一会话把同一个问题问两遍，看它会不会说"你是在测试我吗"。（它不是记得你，是你每次都把记忆发它。）
4. **账单**：`/provider anthropic` 后连聊几轮，每轮 `/usage` 看涨幅。涨幅和你这句话的字数对不上——差额是历史。
5. **中断**：让它写个长代码，写到一半 Ctrl+C，然后问"我上一句回答到哪了"。
6. **断网**：关 Wi-Fi 再提问，看退避日志；开网后它会自己缓过来吗？（试完告诉我。）

## 九、下一步

阶段 0 到此收官。现在的 mini-coder 有了 provider 翻译官、SSE 流式、结构化错误、一个会失忆也会续命的 REPL——但它只会聊天，不会动手。

下一阶段它开始"像 Claude Code"的真正一步：**工具调用**。让模型说"我要读某个文件"，程序替它执行、把结果喂回去，循环往复。第三节埋的伏笔 `finish_reason` 到时会以 `"tool_calls"` 的形态登场。
