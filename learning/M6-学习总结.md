## 一、核心概念（学到了什么）

### 1. MCP（Model Context Protocol）——了解即可，不实现

- 解决的问题：**M×N 集成爆炸**——M 个模型客户端各自对接 N 个工具服务，每对都要写一遍认证/协议代码；MCP 把它变成 M+N（各自实现一次统一协议）
- 对 mini-coder 的关系：mini-coder 的工具是**自己写在本地的**（read/write/bash），不经过 MCP；MCP 是"接入第三方服务生态"时的标准答案——阶段 0 不做，知道它站在哪里即可

### 2. 《Building Effective Agents》核心区分：workflow ≠ agent

- **workflow**：人预先写死流程，模型在固定环节被调用——控制流在代码里
- **agent**：模型自己决定下一步做什么、用哪个工具——控制流在模型手里
- 判断标准一句话：**"谁在决定下一步"**——代码决定是 workflow，模型决定是 agent

### 3. 四个同类实现的最小公约数（详见 NOTES 调研栏）

> **agent = LLM + 循环 + 足够的 token**（Amp 原话，我们 M3 已用 ~25 行验证）

- 同一个循环骨架：`while 未结束: 调 LLM → 解析动作 → 执行 → 结果回填`
- 客户端持有会话：模型服务端无状态，每轮全量重发
- 终止两件套：模型自答 或 硬限额
- 工具调用本质 = 特殊文本 → 本地解析执行 → 结果回填；工具集都极小（3 个文件工具 / 1 个 bash）
- 错误喂回模型自愈，而非代码层重试

### 4. Anthropic SDK 剖析文的循环公式（比 Amp 高一层）

**gather context → take action → verify work → repeat**

- Amp 讲"循环怎么写"（内核），Anthropic 讲"循环每一步该给模型什么能力"（方法轮）
- **verify work 三手段**（由硬到软）：规则（lint 报错喂回）→ 视觉反馈（截图喂回）→ LLM as judge（另一个模型评语喂回）——共同哲学：**检验的产出最终都是文本，喂回上下文让模型自己修**
- gather context 的反直觉结论："文件系统就是 context engineering"；**先 agentic search（让模型 grep），后语义检索**——语义检索更快但更不准、更难维护、更不透明
- compaction 官方确认 = 客户端在上下文逼近上限时自动摘要改写 messages（M1 观察的正式出处）
- subagent 的本质是**上下文的过滤器**，不只是"更多的大脑"

### 5. 带读模式（本模块的方法论收获）

英文长文直接读：解码成本和思考抢同一块工作记忆，"意思能捕捉但很难受"。改为带读（保留英文原句 + 中文翻译讲解 + 分段 checkpoint）后负担消失。**原文的价值在保真（引用不变形），不在语言本身**——解码苦力可以转移给 AI，思考不能。

### 调研（2026-09-10 晚）

### 原文带读（2026-09-11）

两篇必读按"原句 + 译 + 讲 + checkpoint"方式带读完成（自读模式因英文阅读负担改为带读，见核心概念 5）。带读中的关键原句：

- Amp："It's an LLM, a loop, and enough tokens" / "If it's an error, we flip a boolean. That's it."（错误自愈=翻个布尔值，没有代码层重试）/"Anything goes as long as Claude can make sense of it"（工具返回格式无规定，模型看得懂就行，靠实验发现）/"Claude 3.7 loves replacing strings (experimentation is how you find out what they love)"（工具设计迁就模型的天然习惯）
- SDK 文："give your agents a computer, allowing them to work like humans do" / "they catch mistakes before they compound"（verify 的价值：错误滚雪球前拦住）

### 费曼检验（2026-09-11，收官答辩题）

**题**：SDK 文循环里的 "verify work"，我们 M5 的 agent-hardened.mjs 里有对应机制吗？

**学员原答**：三件套本身都是一种检验——把错误信息/判断信息塞给 LLM 让模型进一步处理，更偏向规则检验。

**判卷：通过 ✅（本质答对：检验 = 把判断变成文本喂回模型），一处偏差修正**——三件套不能一锅端，各自站在循环不同位置：

| M5 机制 | 循环位置 | 算 verify work 吗 |
|---|---|---|
| 重试退避 | `LLM(messages)` 失败时 | ❌ 重发同一请求，无信息喂给模型，是"通信抢修" |
| 权限分级 | 行动**之前**拦截 | ⭕ 半个——拒绝结果回传算规则检验，但裁决者是人、规则是硬的 |
| 中断存档 | 循环之外 | ❌ 纯状态持久化 |
| 错误脱敏回传 | 工具失败后 | ✅ 最标准的 verify work（rules 手段的最小形态） |

**关键区分**：M5 的检验是**被动的**（出错才触发）；SDK 文的 verify 是**主动的**（没错也检查产出好不好）。缺的"主动自检"恰好 = ROADMAP 阶段 3 的"反思与计划：执行后自检"——学习路线缺口与下一步规划严丝合缝。

## 三、意外发现

1. **我们在 M5 做了四家"最小实现"都没做的事**（退避重试、权限分级、中断存档、错误脱敏）——学习路线的选择恰好补在"最小实现"与"可用产品"的鸿沟上（NOTES 调研栏的对照结论）
2. **"皇帝没穿衣服"**：Amp 整篇都在等读者发现"没有兔子"，agent 内核就那么大；强大不来自核心复杂，来自核心外的工程苦活（elbow grease）
3. **工具设计迁就模型**：edit_file 就是字符串替换，理由是"Claude 喜欢替换字符串"——一切以模型实际表现为准，不靠工程美学想象（与 M2"description 质量决定行为质量"同源）
4. **带读模式被验证有效**：抵触感的根源是英文解码成本而非内容本身；换成"原句+译+讲"后学习体验立刻改善——后续英文材料默认带读

## 五、学习路线收官结论

M1–M6 全部完成。六个模块合起来回答了 LEARNING.md 总览那张图里的全部问题：

- M1：`LLM(messages)` 是什么 → 无状态的文本进文本出，记忆是重发出来的

- M5：历史滚长/出错/越权怎么办 → compact + 重试退避 + 权限分级 + 中断存档
- M6：别人怎么做、还缺什么 → 四实现最小公约数 + verify work 是下一块拼图
