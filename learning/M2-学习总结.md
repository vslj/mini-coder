## 一、核心概念（学到了什么）

### 1. 本模块的第一句话：Agent 的很大作用就是维护请求体

模型永远不帮你管 messages——它只根据你发来的请求体作答。问题、工具说明书、历史回答、工具结果，**全部由客户端塞进请求体**。mini-coder 本质上就是一个请求体管理器。

### 2. 一轮工具调用 = 两次请求（数据结构版全流程）

**① 第一次请求**：`tools`（JSON Schema 说明书）与 `messages` 是**平级字段**，不是塞在消息里；因此每次请求都重发、都计费。

**② 第一次响应**：`finish_reason: "tool_calls"`（M1 伏笔回收），意图在 assistant 消息的 `tool_calls` 数组里：

```jsonc
{ "finish_reason": "tool_calls",
  "message": { "role": "assistant", "content": "",
    "tool_calls": [
      { "id": "call_85d64cec...", "function": { "name": "get_current_time", "arguments": "{}" } },
      { "id": "call_6f5a1a0c...", "function": { "name": "get_weather", "arguments": "{\"city\": \"北京\"}" } }
    ] } }
```

**③ 程序端执行**：模型只"说"不"做"，执行权永远在客户端；逐个 `JSON.parse(arguments)`（它是字符串不是对象）→ 调本地函数。

**④ 第二次请求**：messages 从 1 条涨到 4 条——原 user + **回填的 assistant 消息**（tool_calls 原样带回，模型无状态，不回填就失忆）+ **每条结果一条 `role:"tool"` 消息**（`tool_call_id` 与调用 id 对号入座，`content` 是序列化后的文本）。

**⑤ 第二次响应**：`finish_reason: "stop"`、`tool_calls: null` → 没有新的调用意图，可以停。

### 3. 工具只是一份说明书

模型看不见工具的代码，name/description/parameters 这几十个字就是它的全部决策依据。**说明书质量直接决定参数质量**（实验 2 实证）。参数错误率 = 模型能力 × 说明书质量。

### 4. 参数 JSON 不可信，服务端不校验

schema 是格式说明书不是校验器；模型可能拼错参数、缺字段、调不存在的工具，错误直达客户端。客户端必须自己 parse + 验证 + 兜底（失败时把错误作为 tool_result 回传让模型自纠——M5 伏笔）。

### 5. 执行权在客户端 ⇒ 权限确认能存在

程序在"模型说了想调用"和"实际执行"之间有一个可插手的时刻（确认弹窗/权限分级）。弹窗的也是程序——模型全程不知道有权限这回事。

### 6. 选工具行为的全谱系（实验 3）

| 场景 | 行为 |
|------|------|
| 参数齐全、多工具都用得上 | 一次响应里 `tool_calls` 数组多项并存（parallel tool calls） |
| 参数缺失（没说城市） | 只调能调的，反问用户补参数 |
| 与工具无关 | `tool_calls: null` 直接回答 |

### 7. Provider 差异清单 +1

OpenAI 兼容协议叫 `tool_calls` / `finish_reason:"tool_calls"`；Anthropic 原生协议叫 `tool_use` 块 / `stop_reason:"tool_use"`。MiMo 平台两个端点都提供（`/v1` 与 `/anthropic`）——provider 抽象层的活教材。

## 二、实验记录（亲手验证了什么）

### 实验 1：完整两步请求（exp1-weather-tool.mjs，主线）

假工具 `get_weather(city)`（写死返回 22°C 晴），问"北京今天天气怎么样？适合跑步吗？"。

第一次响应关键观察：
- `content: ""` —— MiMo 一句客套话没有，意图全在 `tool_calls`
- `arguments` 原文 `"{\"city\": \"北京\"}"` —— 字符串里的 JSON，转义地狱第二现场
- 思维链照旧在 `reasoning_content`

第二次请求前 messages 演变：user → assistant(tool_calls) → tool(tool_call_id 对号) ，模型拿到假天气后**照单全收**，还基于"晴、22°C"给出防晒建议——它对 tool_result 零怀疑。

Token 实测（本轮通道 MiMo）：

| 请求 | prompt_tokens | cached_tokens | 备注 |
|------|--------------|---------------|------|
| 第一次 | 526 | 256 | 含工具说明书 |
| 第二次（带 tools） | 644 | 512 | 526 + 回填两条 ≈ 644 ✅ |
| 第二次（不带 tools，旧版脚本） | 372 | 192 | 引发"破案"，见意外发现 1 |

### 实验 2：模糊描述对照（exp2-vague-tool.mjs）

同一问"上海明天会下雨吗？"：

- **烂说明书**（`search(input)`，description 仅"搜索。"）：`arguments` = `{"input": "上海明天天气预报 下雨"}` ——模型把工具脑补成搜索框，塞进一串**搜索引擎式人话**
- **好说明书**（`get_weather(city, date)`，逐参数说明）：`arguments` = `{"city": "上海", "date": "明天"}` ——干净的结构化参数

差异只来自 description 那几十个字。

### 实验 3：双工具选择（exp3-two-tools.mjs）

- 问"现在几点了？距离周末还有几天？天气适合出行吗？"（**不说城市**）：只调 `get_current_time({})`，然后**反问"您在哪个城市呢？"**——没有瞎猜城市硬调天气
- 改问"**北京**现在几点？天气适合出行吗？"：`tool_calls` 数组**一次两项**（时间 + 天气），reasoning 原文："这两个调用之间没有依赖关系，所以可以同时进行"——parallel tool calls 实锤，也解释了 `tool_call_id` 为何必须存在
- 问"帮我写一句鼓励学习编程的话"：`finish_reason: "stop"`、`tool_calls: null`——工具在手，无关时忍住不调

### 破案实验：token 口径之谜（probe-usage.mjs）

控制变量：相同请求体连发两次 + 完整两步流程。结论见意外发现 1。

## 三、意外发现（这些最值钱）

1. **"token 不是累加的"破案记**：exp1 第二轮 prompt_tokens 372 < 第一轮 526，违反"输入只增不减"。假设一（平台上报口径不标准）被控制变量实验**证伪**（相同请求体两次 token 完全一致 518=518）；真凶是**旧版脚本第二轮没带 `tools`**，少发了 ~272 token 的说明书。教训与收获各一：脚本不要预写结论（判读是人的工作）；**续轮请求可以不带 tools 省钱**——真实 Agent 的合法优化手段
2. **缓存命中看得见**：`cached_tokens ⊆ prompt_tokens`，MiMo 完全符合标准语义（此前"口径不标准"的怀疑被数据推翻）。同一前缀重跑，cached 从 256→512——跑得越多命中越多、越便宜。M5 成本管理的种子
3. **模型对 tool_result 照单全收**：写死的假天气数据，模型不仅信了还延伸出防晒建议。工具结果说什么它信什么——投毒/越权数据的入口之一（M5 安全的种子）
4. **参数缺失时行为不稳定**：这次反问城市，换个问法可能幻觉一个城市硬调。策略要靠 system prompt 钉死（M4 伏笔）
5. **MiMo 上报怪癖**：`reasoning_tokens: 0` 但消息里明明有 `reasoning_content`——usage 与 message 自相矛盾，又一处"文档说 A 实测 B"
6. **实验通道切换**：本模块中途由 DeepSeek 切到小米 MiMo。MiMo 同时提供 OpenAI 兼容（`/v1`）和 Anthropic 原生（`/anthropic`）双端点，且 reasoning/cache 行为与 DeepSeek 高度相似——切换成本极低，恰好验证了"M1 就把请求结构学对"的价值

## 四、博客素材点（可直接取用）

- **"我以为 token 是累加的，直到数字开始变小"**——完整破案故事：观察→假设→控制变量→证伪→归因→预测验证，一篇 博客②的骨架已经有了
- **几十个字的说明书决定参数质量**：`search(input)` 塞人话 vs `get_weather(city, date)` 出结构——写好工具描述是 Agent 工程的核心工作
- **模型把假天气当了真**：22°C 是我编的，它却认真讨论起防晒——tool_result 的信任模型
- **它也会说"不知道"**：没给城市时模型反问而不是瞎猜——但这是运气不是保证，策略必须由你钉死
- **权限弹窗从来不是模型弹的**：执行权在客户端，是权限确认机制能存在的全部前提

## 五、检验问答（费曼自测，2026-09-10 通过）

**Q1 tool_use 和 tool_result 在 messages 里分别是什么 role、什么结构？**
> 初答：assistant 和 tools，对象数组。
> 复盘：意图不是独立消息，是 assistant 消息里的 `tool_calls` 数组（每项含 id + function{name, arguments字符串}）；结果的消息 role 是 `"tool"`（单数），结构 `{role:"tool", tool_call_id, content}`，content 是序列化文本。

**Q2 模型返回的参数 JSON 可信吗？不符合 schema 会怎样？**
> 初答：不知道。
> 复盘：不可信。服务端不校验 schema，错误直达客户端；客户端必须自己 parse + 验证 + 兜底。错误率 = 模型能力 × 说明书质量。mini-coder 的做法：校验失败把错误作为 tool_result 回传让模型自纠。

**Q3 为什么"执行权在客户端"是权限确认机制能存在的前提？**
> 初答：因为工具在用户端。
> 复盘：因为执行发生在程序里，"模型说了想调用"和"实际执行"之间存在可插手时刻——确认、分级、拒绝都发生在这里。若执行在模型/服务端，请求直接生效，连拦的机会都没有。

**终极复述（口语五步，已通过）**：发起问题并把工具说明书放进请求体 → 模型分析出要调工具 → 程序决定给不给权限、执行工具 → 结果回传进请求体 → 模型生成最终回答。数据结构版见"核心概念 2"。

**收束认知（用户自己的话）**：LLM 没有记忆，Agent 的很大作用就是维护请求体——问题、工具、历史全塞进去；工具调用是模型与程序之间的通信；模型对工具只说不做，也可能不调直接答；它可能答错，参数也可能拼错——所以客户端永远要防御。
