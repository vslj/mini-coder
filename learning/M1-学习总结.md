# M1 学习总结：LLM API 的本质

> 完成日期：2026-09-09 ｜ 实验通道：DeepSeek API（OpenAI 兼容协议）
> 本文是学习沉淀 + 博客素材库。`sk-xxx` 为脱敏占位符。

---

## 一、核心概念（学到了什么）

### 1. 模型是无状态的 —— 本次学习最重要的一个事实

模型本身没有记忆。所谓"多轮对话"，是**客户端每次把完整历史重新发一遍**：

- `/clear` 能"失忆"，只是清空了客户端手里的 messages 数组
- `/compact` 能省 token，是客户端把长历史摘要成短文本替换掉
- 模型每次做的事：**给定全部历史，预测下一段最可能的文本**——历史就是它的全部世界

### 2. messages 数组

三种角色：`user` / `assistant` / `system`（Anthropic 把 system 作为顶层参数，OpenAI 兼容协议是 `role:"system"` 的第一条消息——provider 差异的第一个实例）。
响应 = 往数组末尾"续写"一条 assistant 消息。**整个 mini-coder 就是在维护和增长这个数组，没有别的状态。**

### 3. token 与上下文窗口

- 计费按 token，输入输出分开，输入便宜于输出
- 上下文窗口 = 单次请求里"全部 messages + 回复"的总预算
- 历史不免费：每轮对话都把之前的所有内容重发一遍、重算一遍钱

### 4. 流式输出（SSE）

- `"stream": true` 后服务端逐块推送 `delta`（增量），客户端边收边拼
- 拼接后的完整文本 == 非流式的那条 assistant 消息
- **流式不省 token 不省钱，只省"等待感"**

## 二、实验记录（亲手验证了什么）

### 实验 1：裸调 API（curl，不用 SDK）

用 PowerShell here-string + `curl.exe` 发了一个最小请求体——一条 system 提示加一句问候，就这么点东西：

```powershell
PS> $body = @'
{"model": "deepseek-v4-pro", "messages": [{"role": "system", "content": "You are a helpful assistant."}, {"role": "user", "content": "你好，用一句话介绍你自己"}], "stream": false}
'@

PS> curl.exe -s https://api.deepseek.com/chat/completions `
      -H "Content-Type: application/json" `
      -H "Authorization: Bearer sk-xxx" `
      -d $body
```

服务端原样砸回来一坨单行 JSON——这就是不套任何 SDK 时，你直接面对的东西：

```json
{"id":"009db93e-6c7e-4843-ade4-6020d63261d6","object":"chat.completion","created":1788944834,"model":"deepseek-v4-pro","choices":[{"index":0,"message":{"role":"assistant","content":"你好，我是一个智能助手，致力于用简洁准确的方式帮助你解答问题、提供信息和建议。","reasoning_content":"我们需要回答用户请求。用户说"你好，用一句话介绍我自己"。需要注意中文。需要一句话介绍自己。我们作为AI助手。应该简洁。可以说"你好，我是一个智能助手，致力于用简洁准确的方式帮你解答问题、提供信息和建议。" 一句话。确保不要用"我自己"混淆？用户说"用一句话介绍你自己"即介绍我。需要一句话。可以。"},"logprobs":null,"finish_reason":"stop"}],"usage":{"prompt_tokens":95,"completion_tokens":100,"total_tokens":195,"prompt_tokens_details":{"cached_tokens":0},"completion_tokens_details":{"reasoning_tokens":80},"prompt_cache_hit_tokens":0,"prompt_cache_miss_tokens":95},"system_fingerprint":"a307abda487cd1b463329ccb945ce396"}
```

最有意思的是 `reasoning_content`：一句 20 字的回答，背后居然拖着这么长一段"草稿"。观察到的关键字段：

| 字段 | 值 | 含义 |
|------|-----|------|
| `choices[0].message.content` | 正式回答 | 模型的"正文" |
| `choices[0].message.reasoning_content` | 打草稿的过程 | DeepSeek 的思维链，独立于 content |
| `choices[0].finish_reason` | `"stop"` | 自然说完；**将来工具调用时会变成 `tool_calls`（M2 的伏笔）** |
| `usage.prompt_tokens` | 95 | 输入文字撑死 30 token，多出来的 65 是协议开销 |
| `usage.completion_tokens` | 100（其中 `reasoning_tokens: 80`） | **80% 的输出 token 花在了"打草稿"上** |

### 实验 3：流式请求

请求只多一个参数：

```json
{"model": "deepseek-v4-pro", "messages": [{"role": "system", "content": "You are a helpful assistant."}, {"role": "user", "content": "你能编程吗？"}], "stream": true}
```

响应从"一个 JSON 对象"变成了一条 **SSE 流**——`data: {...}` 一块块往外蹦，每块带 `delta`（增量）。真实输出有几十块，这里节选关键节点：

```text
# 开头：第一块，delta 里什么内容都没有，只是一个"开场信号"
data: {"id":"5b985e80-...","object":"chat.completion.chunk","created":1788945476,"model":"deepseek-v4-pro","choices":[{"index":0,"delta":{"role":"assistant","content":null,"reasoning_content":""},"logprobs":null,"finish_reason":null}]}

# 推理阶段：一块一个词，全部落在 reasoning_content 上
data: {"id":"5b985e80-...","choices":[{"index":0,"delta":{"content":null,"reasoning_content":"我们需要"},"logprobs":null,"finish_reason":null}]}
data: {"id":"5b985e80-...","choices":[{"index":0,"delta":{"content":null,"reasoning_content":"回答"},"logprobs":null,"finish_reason":null}]}
data: {"id":"5b985e80-...","choices":[{"index":0,"delta":{"content":null,"reasoning_content":"用户"},"logprobs":null,"finish_reason":null}]}
（中间几十块推理 delta 略……）

# 转折：reasoning_content 终于null了，content 开始出现——草稿打完，正文开写
data: {"id":"5b985e80-...","choices":[{"index":0,"delta":{"content":"是的","reasoning_content":null},"logprobs":null,"finish_reason":null}]}

# 正文阶段：一块一个词
data: {"id":"5b985e80-...","choices":[{"index":0,"delta":{"content":"，我可以帮你：\n\n","reasoning_content":null},"logprobs":null,"finish_reason":null}]}
（正文 delta 略……）

# 收尾：最后一块 finish_reason 落定为 "stop"，然后一行 data: [DONE] 结束整个流
data: {"id":"5b985e80-...","choices":[{"index":0,"delta":{},"logprobs":null,"finish_reason":"stop"}]}
data: [DONE]
```

观察结论：
- **分界清晰**：前面所有块推 `reasoning_content`（草稿），推完才开始推 `content`（正文）——两种 delta 的接力
- `finish_reason` 一路 `null`，最后一块才落定为 `"stop"`；协议以 `data: [DONE]` 收尾

## 三、意外发现（这些最值钱）

1. **`reasoning_content` 不应回传**：DeepSeek 官方文档说下一轮请求不应包含它，但带着回传也跑通了（服务端宽容忽略）→ 每家 provider 对"历史里该带什么"规则不同，**这是必须做 provider 抽象层的现实证据**
2. **`prompt_cache_hit_tokens: 0` 字段的存在**：说明有提示词缓存机制（重复前缀命中缓存可省钱），M5 再展开
3. **密钥管理教训（亲身踩坑）**：实验时把真实 key 原文贴进了对话 → 立刻作废重发。规则：key 只放环境变量/`.env`（进 `.gitignore`）；对外展示一律 `sk-xxx`

## 四、博客素材点（可直接取用）

- **开场观察**："我让它回答一句话，它却先打了两倍长的草稿"——usage 里 `reasoning_tokens: 80 / completion_tokens: 100`，输出 token 大头花在思考上
- **"记忆是我发的"体感**：两轮对话 prompt_tokens 95→123 的对比，比任何解释都直观
- **95 的输入只有 30 是人话**：协议开销的"隐形成本"，引出 Agent 成本意识
- **流式的分界现象**：先推思维链再推正文，"打字机效果"背后是两种 delta 的接力
- **key 泄露的小事故**：真实开发中第一课不是写代码，是别把钥匙贴墙上

## 五、检验问答（费曼自测，2026-09-09 通过）

**Q1 为什么第二次调用必须带上第一次的回复？**
> 模型没有记忆功能，只能根据上下文接上对话。

（补全：更准确的机制是"给定全部历史预测下一段文本"，所以历史决定一切——包括将来调什么工具、传什么参数。）

**Q2 上下文窗口满了会怎样？Claude Code 怎么应对？**
> 工具会提示进行 compact，有百分比提示；有些模型自动压缩，Claude 工具也会自动压缩。

（补全：这些动作全部是**客户端**在改 messages 数组——摘要替换长历史——不是模型有记忆管理能力。）

**Q3 流式和非流式的差异？**
> 流式请求体 `stream:true`，响应一点点持续返回；非流式 `stream:false`，一次性返回结果。

（补全：非流式响应是完整 JSON 对象，流式响应是 SSE 数据流，每块是 `delta` 增量，客户端负责拼接。）
