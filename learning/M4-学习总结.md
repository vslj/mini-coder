## 一、核心概念（学到了什么）

### 1. System prompt 的三句话

- 它是 **messages 数组的第一条消息**（`role:"system"`，OpenAI 兼容协议；Anthropic 协议是顶层参数——provider 差异清单第三处），结构与 user 消息完全相同：`{role, content}`
- 它是给模型的**岗位说明书**：身份、规则、输出格式、工具使用策略。工具级行为靠工具的 description（M2），**跨工具的全局行为靠 system prompt**（M4）
- **规则是"请求"不是"强制执行"**：模型可能遵守也可能不遵守。真正的强制力在客户端执行器——软约束引导 + 硬约束兜底

### 2. 本模块最重要的实验发现：规则的价值是"钉死"不是"变好"

三连跑同一任务（"把 hello.txt 更新成：世界，你好"）：

| 组 | 第一轮行为 | 最终回答 |
|----|-----------|---------|
| agent.mjs（无规则） | `read_file`（自己选择先读） | 长回答 + 主动提供后续选项 |
| agent2 --bare（无规则对照） | `write_file`（**凭空覆盖**） | 简短一句 |
| agent2 带规则 | `read_file`（规则 1 生效） | 一句话汇报 |

两个"无规则"组行为**分裂**了——一个先读一个盲写。结论：无规则时模型靠临场发挥，发挥有好有坏、每次可能不同；system prompt 把好行为从**概率事件变成默认动作**。它买的是确定性，不只是质量。

### 3. 软硬约束的合龙（与 M2"执行权在客户端"对接）

- 软约束：system prompt 规则，说给模型听，可能被违反
- 硬约束：执行器校验——程序维护"本会话已读过哪些文件"的状态，`write_file` 时查表，没读过就**拒绝执行**，并把违反原因作为 tool_result 回传让模型自纠
- 拦截依据是**会话状态**，不是"第几轮"这种表面特征
- 这就是 Claude Code 权限确认不可绕过的原因——哪怕 system prompt 被注入攻击，执行器照样拦

### 4. few-shot（概念已建立，未单独实验）

在 messages 里放示范对话，模型会模仿——比规则更软，但常常更有效。与规则的取舍：规则给边界，few-shot 给"手感"。

### 5. 实验设计的方法论（本模块的意外收获）

- **任务要能激发被测行为**：想测"简短汇报"规则，就得用会引出长篇大论的任务——本次任务只会引发简短回答，规则 2 无从对照
- **对比实验要重置共享状态**：hello.txt 的内容在几组之间被上一次运行改过，实验组读到的不是"原始状态"
- **token 只在请求体逐字节相同时才可比**（M2 破案实验的推论），跨运行比较被缓存状态和思维链长度污染

## 三、意外发现

1. **无规则组的行为分裂**（本模块最大发现，见核心概念 2）
2. **规则密度问题**：system prompt 每轮重发、位于最前，模型遵循度通常高于中后段消息——但规则塞太多会互相稀释，要少而硬
3. **实验会污染自己**：Agent 的每次运行都改写沙盒状态，"上次运行"是"这次实验"的隐藏变量

## 五、检验问答（费曼自测，2026-09-10 通过）

**Q1 system prompt 在 messages 里是什么 role、什么位置？结构和 user 消息有区别吗？**
> 答：role 是 "system"，在消息数组顶部；结构没区别，都是 {role, content}。
> 补全：Anthropic 协议中它是顶层参数而不是消息——provider 抽象层第三处差异。

**Q2 有规则必须被强制执行（如"禁止删除文件"），只写进 system prompt 够吗？**
> 答：不够，程序要有自己的兜底，判断到 delete 类调用时直接在权限上拒绝。
> 补全：精确形态是执行器查策略表 + 拒绝理由作为 tool_result 回传让模型自纠；拦截看会话状态不看轮数。

**Q3 "规则是请求不是强制"的对错两面？**
> 答：对的面——规则是请求体的一部分，希望模型按它执行，但执不执行是模型自己的决策，所以不是强制。错的面——它是请求体的一部分，不是字面上的一个"请求"。
> 补全：它虽不强制，但比普通消息约束力更强（每轮重发、位于最前）；且规则密度要低，多了互相稀释。
