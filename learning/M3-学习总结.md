## 一、核心概念（学到了什么）

### 1. Agent 的定义（一句话）

**Agent = 把 M2 的"一轮工具调用"放进 while 循环，直到模型不再要求调用工具。**
M3 没有新的协议知识，全部是把 M2 的结构循环起来。

### 2. 毕业版伪代码（费曼默写修正后定稿）

```
messages = [用户任务]
while true:
    response = LLM(messages, 工具说明书)
    if response.finish_reason !== "tool_calls":
        输出 response.content        # 最终回答，交给用户（不是 tool_result！）
        break
    messages.push(response 那条 assistant 消息)          # 回填模型的话
    对 response 里每个 tool_call:
        结果 = 本地执行(tool_call)
        messages.push({ role:"tool", tool_call_id, 结果 })  # 回填执行结果
```

### 3. 两个停止条件，缺一不可

- **自然停**：`finish_reason !== "tool_calls"`——模型认为任务完成（M2 已见过 `stop` + `tool_calls: null`）
- **强制停**：最大迭代上限——防死循环（有错一直调、原地打转）、防无限烧 token。上限是**兜底不是优化**

### 4. "想→做→看结果→再想"的对应物

每一轮：`reasoning_content` 是"想"，程序执行工具是"做"，回填 messages 是"看结果"，下一轮请求是"再想"。thinking 不是循环外的特殊步骤，是每轮决策前的常规环节。

### 5. 错误也是给模型的反馈

工具执行失败**绝不能让程序崩**——把错误信息作为 tool_result 回传，模型拿到 `{error: "ENOENT..."}` 后会自己调整（本实验中它选择停下来问用户，而不是盲目重试）。

### 6. "忘"永远是客户端的锅

模型的世界 = 请求体里有什么。执行到一半"忘了"工具结果，只可能是请求体层面的事：漏回填、中途掐断后没带 messages 续跑、上下文超限被截断/压缩。M5 的 /compact 就是主动"让它忘"再换摘要。

## 二、实验记录（裸 Agent 实测，agent.mjs）

工具：真实的 `read_file` / `write_file`（限沙盒目录 learning/m3/sandbox/），默认上限 8 轮。

| 任务 | 轮数 | messages 演变 | 现象 |
|------|------|--------------|------|
| 1. 创建 hello.txt | 2 | 1→3 | 一轮写完 + 一轮收尾自然停 |
| 2. 读 hello.txt 追加内容另存 | 3 | 1→3→5 | 读→写存在**依赖关系，强制串行**，多轮的本质 |
| 3. 读不存在的 nofile.txt | 2 | 1→3 | 程序没崩，模型拿到错误后**停下来反问用户** |
| 4. 创建 a/b/c 三个文件（上限 2） | 2 | 1→5 | **没触发强制停**：三个写操作无依赖，模型一轮并行全调 |
| 5. 读→复制→再复制（上限 2） | 2（被掐断） | 1→3 | **强制停实锤**，见下 |

任务 4 的教训：想观察强制停，必须用**依赖串行**的任务——并行调用会把多步压进一轮。

强制停（任务 5）的三个"指纹"：
1. **没有最终回答**——循环被掐断，模型没机会说收尾的话，程序手里只有强制停止通知
2. **磁盘半成品**——hello2.txt 已写好，hello3.txt 不存在；强制停不回滚
3. **钱已花**——已跑轮次的 token 照付，工作却没交付

恢复路径：状态全在 messages 数组 + 磁盘里，带着 messages 提高上限重发即可续跑——mini-coder 将来要实现的能力。

## 三、意外发现（这些最值钱）

1. **原始错误信息会泄漏环境**：读文件失败的 `{error: "ENOENT: no such file or directory, open 'D:\\workspace\\...\\nofile.txt'"}` 被原样塞进上下文发给模型——本机绝对路径进了请求体。工具结果一字不漏进上下文，错误消息要先加工再回传（M5 安全伏笔）
2. **并行调用会"骗过"迭代上限**：无依赖的多个操作被模型压进一个 tool_calls 数组，上限 2 压不住三个文件。上限约束的是"轮数"不是"工作量"
3. **模型拿到错误后的行为依然不稳定**：本次它反问用户（好行为），换种场景可能盲目重试或幻觉路径——还是那句话，策略要靠 system prompt 钉死（M4）

## 四、博客素材点（可直接取用）

- **"我写了个 50 行的程序，它自己把活干完了"**——毕业实验本身就是博客③的开场
- **强制停的三个指纹**：没有最终回答、磁盘半成品、钱已花——Agent 的失败模式讲透一行 while 循环的价值
- **错误是燃料不是毒药**：ENOENT 变成 tool_result，模型自己拐弯——"错误也是反馈"是 Agent 健壮性的第一原则
- **并行调用 vs 依赖串行**：模型自己判断能不能一轮干完——工具调用的"调度艺术"

## 五、检验问答（费曼自测，2026-09-10 通过）

**Q1 默写最简 agent 循环伪代码**
> 初答：`while(i<p): if(!tools_call) call(i); break; else call(i)` ——丢掉了三件关键事。
> 复盘返工后定稿（见"核心概念 2"）：每轮必须调 LLM；停止看 `finish_reason`；工具结果必须回填 messages。另外纠正一处易错点：自然停时输出的是 `response.content`（最终回答），不是 tool_result。

**Q2 为什么必须设最大迭代次数？不设会怎样？**
> 答：如果没有明确的停止触发——比如上轮结果不满意或有错误——模型会一直判断"还要继续调"，call(1)→call(∞)，程序空转、token 浪费。
> 补全：还有原地打转（反复做同一动作）和 messages 越滚越贵的成本曲线。上限是安全兜底。

**Q3 模型执行到一半"忘了"之前工具返回的内容，可能是什么原因？**
> 答：直接原因是请求体没有把上一轮工具结果塞进去；比如循环被中途终止、工具结果还没到达 LLM 就总结，下一段执行就丢了上下文。
> 补全：完整谱系还包括漏回填、截断/压缩（M5 的 /compact 是主动让它忘）。模型自己永远不会忘——它的世界就是请求体。
